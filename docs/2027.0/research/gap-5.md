Research date: 2026-09-03. .NET 11 is at Preview 7 (`11.0.100-preview.7.26381.103`); GA is November 2026.
Every claim below is sourced. Where a primary source could not be found the item is marked **UNVERIFIED**.

`6.0.428, 8.0.424, 9.0.317, 10.0.111, 10.0.303, 10.0.400`). The .NET 10 SDK 10.0.400 was read directly to

## 1. Preprocessor symbols defined for `net11.0`

### 1.1 The mechanism (unchanged in .NET 11)

Symbols are generated by three MSBuild targets in
`src/Tasks/Microsoft.NET.Build.Tasks/targets/Microsoft.NET.Sdk.BeforeCommon.targets`
(installed as `<dotnet>/sdk/<ver>/Sdks/Microsoft.NET.Sdk/targets/Microsoft.NET.Sdk.BeforeCommon.targets`):

- `GenerateTargetFrameworkDefineConstants` (line ~188 in 10.0.400)
- `GenerateTargetPlatformDefineConstants` (line ~212)
- `GenerateNETCompatibleDefineConstants` (line ~234)

Verbatim from the installed 10.0.400 SDK:

```xml
<Target Name="GenerateTargetFrameworkDefineConstants"
        Condition=" '$(DisableImplicitFrameworkDefines)' != 'true' and '$(TargetFrameworkIdentifier)' != '.NETPortable' and '$(TargetFrameworkIdentifier)' != ''">
  <PropertyGroup>
    <_FrameworkIdentifierForImplicitDefine>$(TargetFrameworkIdentifier.Replace('.', '').ToUpperInvariant())</_FrameworkIdentifierForImplicitDefine>
    <_FrameworkIdentifierForImplicitDefine Condition=" '$(TargetFrameworkIdentifier)' == '.NETCoreApp' and $([MSBuild]::VersionGreaterThanOrEquals($(TargetFrameworkVersion), 5.0)) ">NET</_FrameworkIdentifierForImplicitDefine>
    <VersionlessImplicitFrameworkDefine>$(_FrameworkIdentifierForImplicitDefine)</VersionlessImplicitFrameworkDefine>
    <_FrameworkIdentifierForImplicitDefine Condition=" '$(TargetFrameworkIdentifier)' == '.NETFramework'">NET</_FrameworkIdentifierForImplicitDefine>
    <_FrameworkVersionForImplicitDefine>$(TargetFrameworkVersion.TrimStart('vV'))</_FrameworkVersionForImplicitDefine>
    <_FrameworkVersionForImplicitDefine>$(_FrameworkVersionForImplicitDefine.Replace('.', '_'))</_FrameworkVersionForImplicitDefine>
    <_FrameworkVersionForImplicitDefine Condition=" '$(TargetFrameworkIdentifier)' == '.NETFramework'">$(_FrameworkVersionForImplicitDefine.Replace('_', ''))</_FrameworkVersionForImplicitDefine>
    <ImplicitFrameworkDefine>$(_FrameworkIdentifierForImplicitDefine)$(_FrameworkVersionForImplicitDefine)</ImplicitFrameworkDefine>
    <BackwardsCompatFrameworkDefine Condition="'$(TargetFrameworkIdentifier)' == '.NETCoreApp' and $([MSBuild]::VersionGreaterThanOrEquals($(TargetFrameworkVersion), 5.0))">$(TargetFrameworkIdentifier.Replace('.', '').ToUpperInvariant())</BackwardsCompatFrameworkDefine>
  </PropertyGroup>
  <ItemGroup>
    <_ImplicitDefineConstant Include="$(VersionlessImplicitFrameworkDefine)" />
    <_ImplicitDefineConstant Include="$(ImplicitFrameworkDefine)" />
    <_ImplicitDefineConstant Include="$(BackwardsCompatFrameworkDefine)" />
  </ItemGroup>
</Target>
```

The `_OR_GREATER` chain is driven by the item `_NETCoreAppVersionsForDefines` declared in
`Microsoft.NET.SupportedTargetFrameworks.props`, commented in the file as
"Full list used for compiler define generation (NET*_OR_GREATER); never filtered by VS/MSBuild version."
In 10.0.400 the list ends at `.NETCoreApp,Version=v10.0`; the .NET 11 SDK appends
`.NETCoreApp,Version=v11.0`.

```xml
<_ImplicitDefineConstant Include="@(_FormattedCompatibleFrameworkVersions->'$(_FrameworkIdentifierForImplicitDefine)%(Identity)_OR_GREATER'->Replace('.', '_'))"
                         Condition=" '$(TargetFrameworkIdentifier)' != '.NETCoreApp' or $([MSBuild]::VersionGreaterThanOrEquals(%(_FormattedCompatibleFrameworkVersions.Identity), 5.0)) " />
<_ImplicitDefineConstant Include="@(_FormattedCompatibleFrameworkVersions->'NETCOREAPP%(Identity)_OR_GREATER'->Replace('.', '_'))"
                         Condition=" '$(TargetFrameworkIdentifier)' == '.NETCoreApp' and $([MSBuild]::VersionLessThan(%(_FormattedCompatibleFrameworkVersions.Identity), 5.0)) " />
```

### 1.2 The exact symbol set for `<TargetFramework>net11.0</TargetFramework>`

| Kind | Symbols |
|---|---|
| Versionless | `NET`, `NETCOREAPP` |
| Version-specific | `NET11_0` |
| `_OR_GREATER` (.NET 5+ shape) | `NET11_0_OR_GREATER`, `NET10_0_OR_GREATER`, `NET9_0_OR_GREATER`, `NET8_0_OR_GREATER`, `NET7_0_OR_GREATER`, `NET6_0_OR_GREATER`, `NET5_0_OR_GREATER` |
| `_OR_GREATER` (legacy .NET Core shape) | `NETCOREAPP3_1_OR_GREATER`, `NETCOREAPP3_0_OR_GREATER`, `NETCOREAPP2_2_OR_GREATER`, `NETCOREAPP2_1_OR_GREATER`, `NETCOREAPP2_0_OR_GREATER`, `NETCOREAPP1_1_OR_GREATER`, `NETCOREAPP1_0_OR_GREATER` |
| Always | `TRACE` (added unconditionally by `Microsoft.NET.Sdk.CSharp.props`), `DEBUG` in Debug |

There are **no new symbol shapes** in .NET 11. `NET11_0` and `NET11_0_OR_GREATER` follow the mechanical
rule "replace dots and hyphens with underscore, uppercase".

**Collision hazard worth noting:** `NET11` (no underscore) is the .NET Framework 1.1 symbol, and
`NET11_OR_GREATER` is defined when targeting .NET Framework 2.0 and later. The .NET 11 symbols carry the
`_0` suffix (`NET11_0`, `NET11_0_OR_GREATER`), so there is no literal collision, but a hand-written
`#if NET11` intended for .NET 11 silently means .NET Framework 1.1 and will never be true.

Documentation status: `https://learn.microsoft.com/en-us/dotnet/standard/frameworks` and the shared
include `https://github.com/dotnet/docs/blob/main/includes/preprocessor-symbols.md` (checked
2026-09-03) still stop at `NET10_0` / `NET10_0_OR_GREATER`; the docs page is maintained as a
"latest stable" page and has not been updated for the .NET 11 preview.
Opt-out property: `DisableImplicitFrameworkDefines`.

Sources:
- Installed SDK 10.0.400: `Sdks/Microsoft.NET.Sdk/targets/Microsoft.NET.Sdk.BeforeCommon.targets`, `Sdks/Microsoft.NET.Sdk/targets/Microsoft.NET.SupportedTargetFrameworks.props`
- https://learn.microsoft.com/en-us/dotnet/standard/frameworks#preprocessor-symbols

## 2. Every SDK default that differs for `net11.0` versus `net10.0`

### 2.1 `LangVersion` — 14.0 to 15.0

The default is **not** in the .NET SDK; it is in Roslyn's MSBuild task targets,
`src/Compilers/Core/MSBuildTask/Microsoft.CSharp.Core.targets`, deployed as
`<dotnet>/sdk/<ver>/Roslyn/Microsoft.CSharp.Core.targets`. Verbatim from 10.0.400:

```xml
<PropertyGroup>
  <!-- .NETCoreApp < 3.0, .NETStandard < 2.1, or any other target framework -->
  <_MaxSupportedLangVersion Condition="('$(TargetFrameworkIdentifier)' != '.NETCoreApp' OR '$(_TargetFrameworkVersionWithoutV)' &lt; '3.0') AND
                                       ('$(TargetFrameworkIdentifier)' != '.NETStandard' OR '$(_TargetFrameworkVersionWithoutV)' &lt; '2.1')">7.3</_MaxSupportedLangVersion>

  <!-- .NETCoreApp < 5.0, .NETStandard == 2.1 -->
  <_MaxSupportedLangVersion Condition="(('$(TargetFrameworkIdentifier)' == '.NETCoreApp' AND '$(_TargetFrameworkVersionWithoutV)' &lt; '5.0') OR
                                        ('$(TargetFrameworkIdentifier)' == '.NETStandard' AND '$(_TargetFrameworkVersionWithoutV)' == '2.1')) AND
                                        '$(_MaxSupportedLangVersion)' == ''">8.0</_MaxSupportedLangVersion>

  <!--
    Automatically calculate the maximum supported C# language version based on the .NET Target Framework.
    - Pattern: .NET 5.0 uses C# 9.0, .NET 6.0 uses C# 10.0, and so on.
  -->
  <_MaxSupportedLangVersion Condition="'$(TargetFrameworkIdentifier)' == '.NETCoreApp' AND
                                       '$(_MaxSupportedLangVersion)' == ''">$([MSBuild]::Add(9, $([MSBuild]::Subtract($(_TargetFrameworkVersionWithoutV.Split('.')[0]), 5)))).0</_MaxSupportedLangVersion>

  <!-- Cap _MaxSupportedLangVersion if it exceeds _MaxAvailableLangVersion -->
  <_MaxAvailableLangVersion>14.0</_MaxAvailableLangVersion>     <!-- value in SDK 10.0.400 -->
  <_MaxSupportedLangVersion Condition="'$(_MaxSupportedLangVersion)' != '' AND
                                       '$(_MaxSupportedLangVersion)' &gt; '$(_MaxAvailableLangVersion)'">$(_MaxAvailableLangVersion)</_MaxSupportedLangVersion>

  <MaxSupportedLangVersion>$(_MaxSupportedLangVersion)</MaxSupportedLangVersion>
  <LangVersion Condition="'$(LangVersion)' == '' AND '$(_MaxSupportedLangVersion)' != ''">$(_MaxSupportedLangVersion)</LangVersion>
</PropertyGroup>
```

On `dotnet/roslyn` `main` (verified 2026-09-03) the cap is:

```xml
<_MaxAvailableLangVersion>15.0</_MaxAvailableLangVersion>
```

The formula `9 + (major - 5)` therefore yields, and the cap permits, **`LangVersion = 15.0` for
`net11.0`**. This is per-TFM, so a multi-targeted build gets a *different* language version per target
unless `LangVersion` is set explicitly:

| TFM | `_MaxSupportedLangVersion` / default `LangVersion` under the .NET 11 SDK |
|---|---|
| `net472` (any `.NETFramework`) | `7.3` |
| `netstandard2.0` | `7.3` |
| `netstandard2.1` | `8.0` |
| `netcoreapp3.1` | `8.0` |
| `net8.0` | `12.0` |
| `net9.0` | `13.0` |
| `net10.0` | `14.0` |
| `net11.0` | `15.0` |

Related, unchanged: `Microsoft.NET.Sdk.Common.targets` still contains

```xml
<PropertyGroup Condition="'$(EnablePreviewFeatures)' == 'true' And '$(IsNetCoreAppTargetingLatestTFM)' == 'true'">
  <LangVersion>Preview</LangVersion>
</PropertyGroup>
```

and `IsNetCoreAppTargetingLatestTFM` is set in `Microsoft.NET.Sdk.BeforeCommon.targets` (line 327 in
10.0.400) when `_TargetFrameworkVersionWithoutV == NETCoreAppMaximumVersion`. Under the .NET 11 SDK
`NETCoreAppMaximumVersion` becomes `11.0`, so `EnablePreviewFeatures=true` forces `LangVersion=Preview`
only on the `net11.0` leg (in 10.0.400 the value is `<NETCoreAppMaximumVersion>10.0</NETCoreAppMaximumVersion>`
in `sdk/<ver>/Microsoft.NETCoreSdk.BundledVersions.props`, alongside
`<BundledNETCoreAppPackageVersion>10.0.11</BundledNETCoreAppPackageVersion>`).

The Microsoft documentation explicitly warns against `LangVersion=latest`:
"Don't set the `LangVersion` element to `latest`. The `latest` setting means the installed compiler uses
its latest version. The value of `latest` can change from machine to machine, making builds unreliable.
In addition, it enables language features that might require runtime or library features not included in
the current SDK."
(https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/configure-language-version)

### 2.2 `ImplicitUsings` — the implicit using set gains `System.Net.Http.Json`

`src/Tasks/Microsoft.NET.Build.Tasks/targets/Microsoft.NET.Sdk.CSharp.props`.

.NET 10 SDK (10.0.400, installed, lines 26-33):

```xml
<ItemGroup Condition="'$(ImplicitUsings)' == 'true' Or '$(ImplicitUsings)' == 'enable'">
  <Using Include="System" />
  <Using Include="System.Collections.Generic" />
  <Using Include="System.IO" />
  <Using Include="System.Linq" />
  <Using Include="System.Net.Http" Condition="'$(TargetFrameworkIdentifier)' != '.NETFramework'"/>
  <Using Include="System.Threading" />
  <Using Include="System.Threading.Tasks" />
</ItemGroup>
```

`dotnet/sdk` `main` (verified 2026-09-03):

```xml
<ItemGroup Condition="'$(ImplicitUsings)' == 'true' Or '$(ImplicitUsings)' == 'enable'">
  <Using Include="System" />
  <Using Include="System.Collections.Generic" />
  <Using Include="System.IO" />
  <Using Include="System.Linq" />
  <Using Include="System.Net.Http" Condition="'$(TargetFrameworkIdentifier)' != '.NETFramework'"/>
  <Using Include="System.Net.Http.Json" Condition="'$(TargetFrameworkIdentifier)' == '.NETCoreApp' And $([MSBuild]::VersionGreaterThanOrEquals('$(TargetFrameworkVersion)', '11.0'))" />
  <Using Include="System.Threading" />
  <Using Include="System.Threading.Tasks" />
</ItemGroup>
```

So `net11.0` with `ImplicitUsings=enable` gets **eight** global usings; `net10.0` and every lower TFM get
seven (six on `.NETFramework`, where `System.Net.Http` is excluded). This is a real source-compatibility
surface: a user type named `JsonContent`, or an extension method named `GetFromJsonAsync` in an
unimported namespace, can newly become ambiguous on the `net11.0` leg of a multi-targeted build.

`ImplicitUsings` itself has **no SDK default**; it is set by the project templates
(`<ImplicitUsings>enable</ImplicitUsings>`). Unchanged in .NET 11.

The same file also contains, unchanged:

```xml
<NoWarn>$(NoWarn);1701;1702</NoWarn>
<WarningsAsErrors>$(WarningsAsErrors);NU1605</WarningsAsErrors>
<DefineConstants>$(DefineConstants);TRACE</DefineConstants>
```

### 2.3 `AnalysisLevel`, `EffectiveAnalysisLevel`, `WarningLevel`, `EnableNETAnalyzers`

`src/Tasks/Microsoft.NET.Build.Tasks/targets/Microsoft.NET.Sdk.Analyzers.targets`.

Installed 10.0.400:

```xml
<_NoneAnalysisLevel>4.0</_NoneAnalysisLevel>

<_LatestAnalysisLevel>10.0</_LatestAnalysisLevel>
<_PreviewAnalysisLevel>11.0</_PreviewAnalysisLevel>
```

`dotnet/sdk` `main` (verified 2026-09-03):

```xml
<_NoneAnalysisLevel>4.0</_NoneAnalysisLevel>
<_LatestAnalysisLevel>11.0</_LatestAnalysisLevel>
<_PreviewAnalysisLevel>12.0</_PreviewAnalysisLevel>
```

The surrounding logic is unchanged:

```xml
<AnalysisLevel Condition="'$(AnalysisLevel)' == '' And
                          '$(TargetFrameworkIdentifier)' == '.NETCoreApp' And
                          $([MSBuild]::VersionEquals($(_TargetFrameworkVersionWithoutV), '$(_LatestAnalysisLevel)'))">latest</AnalysisLevel>
<AnalysisLevel Condition="'$(AnalysisLevel)' == '' And
                          '$(TargetFrameworkIdentifier)' == '.NETCoreApp' And
                          $([MSBuild]::VersionGreaterThanOrEquals($(_TargetFrameworkVersionWithoutV), '5.0'))">$(_TargetFrameworkVersionWithoutV)</AnalysisLevel>
...
<EffectiveAnalysisLevel Condition="'$(AnalysisLevel)' == 'none' or '$(AnalysisLevelPrefix)' == 'none'">$(_NoneAnalysisLevel)</EffectiveAnalysisLevel>
<EffectiveAnalysisLevel Condition="'$(AnalysisLevel)' == 'latest' or '$(AnalysisLevelPrefix)' == 'latest'">$(_LatestAnalysisLevel)</EffectiveAnalysisLevel>
<EffectiveAnalysisLevel Condition="'$(AnalysisLevel)' == 'preview' or '$(AnalysisLevelPrefix)' == 'preview'">$(_PreviewAnalysisLevel)</EffectiveAnalysisLevel>
```

Consequences:

- Under the .NET 11 SDK, a `net11.0` project with no explicit `AnalysisLevel` gets `AnalysisLevel = latest`,
  which resolves to `EffectiveAnalysisLevel = 11.0`. A `net10.0` project gets the literal `AnalysisLevel = 10.0`.
- `AnalysisLevel=latest` now means **.NET 11 rules**, not .NET 10. Independently, the .NET 11 SDK fixed a bug
  where `AnalysisLevel=latest` was resolving to .NET 9 rules: "Projects with `AnalysisLevel=latest` were
  incorrectly using .NET 9 analyzer rules instead of the expected .NET 11 rules. This is now fixed."
  (https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-11/sdk#analysislevel-corrected-for-net-11;
  see also dotnet/sdk issue 52467). Any project pinned to `latest` therefore sees **two releases' worth of
  new default-on CA rules arrive at once**.
- `AnalysisLevel=preview` now means 12.0 (it meant 11.0 under the .NET 10 SDK), and the compound forms
  (`latest-all`, `preview-none`, `11.0-recommended`, ...) shift with it.

`WarningLevel` (C# warning waves) — verbatim, unchanged logic:

```xml
<WarningLevel Condition="'$(Language)' == 'C#' And '$(WarningLevel)' == '' And '$(AnalysisLevel)' == 'preview'">9999</WarningLevel>
<WarningLevel Condition="'$(Language)' == 'C#' And '$(WarningLevel)' == '' And '$(TargetFrameworkIdentifier)' == '.NETFramework' ">4</WarningLevel>
<WarningLevel Condition="'$(Language)' == 'C#' And '$(WarningLevel)' == '' And '$(TargetFrameworkIdentifier)' == '.NETCoreApp' ">$(_TargetFrameworkVersionWithoutV.Split('.')[0])</WarningLevel>
```

So the default `WarningLevel` is the TFM's *major version*:

| TFM | default `WarningLevel` |
|---|---|
| `net472` | 4 |
| `netstandard2.0` | (none set by the SDK; csc default 4) |
| `net8.0` | 8 |
| `net10.0` | 10 |
| `net11.0` | **11** |

Targeting `net11.0` therefore enables **warning wave 11** on that leg only. Note that Visual Basic gets
`<WarningLevel Condition=" '$(WarningLevel)' == '' ">1</WarningLevel>` from
`Microsoft.NET.Sdk.VisualBasic.props`; that is an unrelated scale.

`EnableNETAnalyzers` and friends — unchanged:

```xml
<!-- Condition on the PropertyGroup: '$(EffectiveAnalysisLevel)' != '' And $([MSBuild]::VersionGreaterThanOrEquals($(EffectiveAnalysisLevel), '5.0')) -->
<EnableNETAnalyzers Condition="'$(EnableNETAnalyzers)' == ''">true</EnableNETAnalyzers>
<EnforceCodeStyleInBuild Condition="'$(EnforceCodeStyleInBuild)' == ''">false</EnforceCodeStyleInBuild>
```

and, for `.NETFramework` / `.NETStandard` (no `EffectiveAnalysisLevel`, or <= 4.0):

```xml
<EnableNETAnalyzers Condition="'$(EnableNETAnalyzers)' == ''">false</EnableNETAnalyzers>
<EnforceCodeStyleInBuild Condition="'$(EnforceCodeStyleInBuild)' == ''">false</EnforceCodeStyleInBuild>
<EnableTrimAnalyzer Condition="'$(EnableTrimAnalyzer)' == ''">false</EnableTrimAnalyzer>
<EnableAotAnalyzer Condition="'$(EnableAotAnalyzer)' == ''">false</EnableAotAnalyzer>
<EnableSingleFileAnalyzer Condition="'$(EnableSingleFileAnalyzer)' == ''">false</EnableSingleFileAnalyzer>
```

`AnalysisMode` default: `Default` (unchanged).

.NET 11 analyzer behaviour changes that are not TFM-gated but arrive with the SDK:
- `CA1873` (Avoid potentially expensive logging): property accesses, `GetType()`, `GetHashCode()` and
  `GetTimestamp()` are no longer flagged; diagnostics apply only to Information-level logging and below by
  default; the message now names the reason (one of: method invocation, object creation, array creation,
  boxing conversion, string interpolation, collection expression, anonymous object creation,
  await expression, with expression).
- `CA1515` and `CA1034` false positives with C# extension members fixed.
- `CA1859` improper handling of default interface implementations fixed.
- New style rule `IDE0410` flags Boolean-flag and `goto` patterns replaceable by labeled `break`/`continue`.

### 2.4 `SdkAnalysisLevel`

Introduced in .NET 9. Default is "the SDK feature band of the running SDK", i.e. **`11.0.100`** under the
.NET 11 SDK. Two documented behaviours attach to the value `11.0.100`
(https://learn.microsoft.com/en-us/dotnet/core/project-sdk/msbuild-props#sdkanalysislevel):

- `NU1703` is emitted when a package uses the deprecated `MonoAndroid` framework assets;
- `NU1019` changes from a warning to an **error** for non-ASCII characters in the `TargetFramework` property.

`SdkAnalysisLevel` version `11.0.100` only respects values down to `8.0.100`.
`SdkAnalysisLevel` is *SDK-wide*, not per-TFM: setting `<SdkAnalysisLevel>10.0.100</SdkAnalysisLevel>`
is the escape hatch that keeps the older SDK/NuGet behaviour for the whole project, including on the
`net11.0` leg.
Design document: https://github.com/dotnet/designs/blob/main/proposed/sdk-analysis-level.md

### 2.6 New SDK-wide behaviours in .NET 11 that are *not* TFM-gated

These change with the SDK, not with `net11.0`, but they change what a compiler-hosting build sees:

- **MSBuild server enabled by default.** Opt out with `DOTNET_CLI_USE_MSBUILD_SERVER=false` or
  `MSBUILDUSESERVER=0`. Also: "The `dotnet` CLI no longer suppresses the MSBuild build server when
  `DOTNET_CLI_USE_MSBUILD_SERVER` is unset. Previously the CLI unconditionally wrote `MSBUILDUSESERVER=0`."
- **NativeAOT `dotnet` CLI host enabled by default.** Opt out with `DOTNET_CLI_ENABLEAOT=false`.
  Fully AOT-served commands: `dotnet --version`, `--info`, `--help`, `<command> --help`, `--cli-schema`,
  `dotnet sln list|migrate|remove`. Tool and external-command launches also resolve from the AOT path.
- **CLI telemetry moved from Application Insights to OpenTelemetry.** The OTLP exporter is now also enabled
  when any `OTEL_EXPORTER_OTLP_*` variable is present, in addition to `DOTNET_CLI_TELEMETRY_ENABLE_EXPORTER`.
  Opt-out remains `DOTNET_CLI_TELEMETRY_OPTOUT`.
- SDK installer deduplication on Linux/macOS via symlinks (Windows "planned for a future preview");
  crossgen skipped for assemblies unique to `DotnetTools/`.
- `dotnet run -e KEY=VALUE`; variables surface to MSBuild as `RuntimeEnvironmentVariable` items.
- "Using launch settings from..." moved from stdout to **stderr**.
- `dotnet test` (Microsoft.Testing.Platform mode) gains `--no-dependencies`, `--use-current-runtime`/`--ucr`,
  `--artifacts-path`, run-level `--timeout` and `--maximum-failed-tests`, traversal-project support,
  the `DOTNET_TEST_RUNNER` environment variable, `!`-prefixed `--test-modules` exclusions,
  two-stage Ctrl+C, and live in-flight test display.
- `dotnet format` accepts `--framework` for multi-targeted projects.
- `dotnet sln` can create and edit `.slnf` solution filters; `dotnet new slnf` exists.
- File-based apps: `#:include` supports `.cs` and now `.dll` (mapped to `Reference` items) without a flag.

### 3.1 Versions

- Targeting pack at Preview 7: **`Microsoft.NETCore.App.Ref` `11.0.0-preview.7.26381.103`**
  (https://github.com/dotnet/core/blob/main/release-notes/11.0/preview/preview7/11.0.0-preview.7.md)

  Compatible with "Visual Studio 18.7 latest preview".
- `NETCoreAppMaximumVersion` in `sdk/<ver>/Microsoft.NETCoreSdk.BundledVersions.props` moves from `10.0`

- **UNVERIFIED**: the assembly version of `System.Runtime` in the .NET 11 ref pack. Every prior release has
  used `<major>.0.0.0`, so `11.0.0.0` is the expected value, but it was not confirmed against the ref pack

### 3.2 Assemblies added: the nine `Microsoft.Extensions.*` libraries

Introduced in **.NET 11 Preview 4**. The following nine libraries are now part of the
`Microsoft.NETCore.App` base shared framework (so they are in the default reference set for `net11.0`
with `Sdk="Microsoft.NET.Sdk"`, with no `FrameworkReference` needed):

1. `Microsoft.Extensions.Caching.Abstractions`
2. `Microsoft.Extensions.Configuration.Abstractions`
3. `Microsoft.Extensions.DependencyInjection.Abstractions`
4. `Microsoft.Extensions.Diagnostics.Abstractions`
5. `Microsoft.Extensions.FileProviders.Abstractions`
6. `Microsoft.Extensions.Hosting.Abstractions`
7. `Microsoft.Extensions.Logging.Abstractions`
8. `Microsoft.Extensions.Options`
9. `Microsoft.Extensions.Primitives`

Documented new behaviour, verbatim:

> - You don't need a `PackageReference` for these libraries when you target `net11.0` or later.
> - If you reference these packages explicitly, you receive build warning NU1510.
> - These assemblies are no longer copied to the output folder.
> - In rare cases, the additional APIs in the default load set might cause name or type conflicts. To
>   resolve a conflict, add more explicit `using` directives, use an alias, or use a fully qualified type name.

The page also lists the historical breaking changes that surface when a project that pinned an old version
of these packages is moved to the .NET 11 versions: `ActivatorUtilities.CreateInstance` behaviour and
non-null-provider requirement, `FromKeyedServicesAttribute.Key` nullability, non-keyed service used when
keyed not found, `GetKeyedService`/`GetKeyedServices` with `AnyKey`, `ProviderAliasAttribute` moved assembly,
unhandled exceptions from a `BackgroundService`, `BackgroundService` running all of `ExecuteAsync` as a Task,
and `IHost.RunAsync`/`StopAsync` throwing when a `BackgroundService` fails.

To avoid `MissingMethodException` / `TypeLoadException`, dependent libraries must be recompiled against the
.NET 11 reference assemblies.

## 4. Framework-type dependencies of each C# 15 / preview feature — the down-level table

This is the load-bearing section. Two Roslyn conventions decide every row:

- **Embedded (synthesized) attributes.** Roslyn generates the attribute type into the assembly itself when
  it is absent, exactly as it has always done for `IsReadOnlyAttribute`, `NullableAttribute`,
  `NullableContextAttribute`, `RefSafetyRulesAttribute`, `ScopedRefAttribute`, `ExtensionMarkerNameAttribute`
  and friends. The feature then works on any TFM.
- **Well-known / predefined types.** Roslyn requires the type to exist and reports `CS0518`
  ("Predefined type '…' is not defined or imported") or `CS0656`
  ("Missing compiler required member '…'") when it does not. A **source-declared polyfill of the correct
  shape satisfies these**, which is exactly the `IsExternalInit` / `RequiredMemberAttribute` /
  `CollectionBuilderAttribute` pattern that PolySharp, Meziantou.Polyfill and SimonCropp/Polyfill implement.

### 4.2 Unions — `UnionAttribute` and `IUnion`

**The compiler does not synthesize them.** The Roslyn test plan for the feature
(https://github.com/dotnet/roslyn/issues/81074) lists under "Misc":
"Missing `UnionAttribute` or `IUnion` types (not synthesized)". It also has a test area
"Unconventional `UnionAttribute` definitions", which implies source-provided definitions are bound and
validated rather than rejected. The csharplang speclet
(https://github.com/dotnet/csharplang/blob/main/proposals/csharp-15.0/unions.md) still carries the open
design question "whether compiler should synthesize missing `UnionAttribute` or `IUnion` types", but both
the implementation and the shipped documentation say they must be supplied.

The .NET 11 Preview 3 C# release notes shipped the polyfill verbatim, which settles the
"is a hand-written declaration accepted" question affirmatively:

```csharp
namespace System.Runtime.CompilerServices
{
    [AttributeUsage(AttributeTargets.Class | AttributeTargets.Struct,
        AllowMultiple = false)]
    public sealed class UnionAttribute : Attribute;

    public interface IUnion
    {
        object? Value { get; }
    }
}
```

(https://github.com/dotnet/core/blob/main/release-notes/11.0/preview/preview3/csharp.md, under
"In preview 3, you need to provide polyfills for the `UnionAttribute` type and the `IUnion` interface in
the `System.Runtime.CompilerServices` namespace.")

The BCL-shipped shape (language reference, and `System.Runtime.cs` ref) is:

```csharp
namespace System.Runtime.CompilerServices;

[AttributeUsage(AttributeTargets.Class | AttributeTargets.Struct, AllowMultiple = false, Inherited = false)]
public sealed class UnionAttribute : Attribute;

public interface IUnion
{
    object? Value { get; }
}
```

Note the discrepancy: the preview-3 polyfill omits `Inherited = false`; the runtime ref assembly has it.

Lowering, verbatim from the language reference. `public union Pet(Cat, Dog, Bird);` becomes equivalent to:

```csharp
[Union] public struct Pet : IUnion
{
    public Pet(Cat value) => Value = value;
    public Pet(Dog value) => Value = value;
    public Pet(Bird value) => Value = value;
    public object? Value { get; }
}
```

The "basic union pattern" the compiler recognizes on any hand-written type:
- a `[Union]` attribute on the type;
- one or more public constructors, each with a single by-value or `in` parameter (each parameter type is a
  case type);
- a public `Value` property of type `object?` (or `object`) with a `get` accessor.

Optional non-boxing access pattern: `bool HasValue { get; }` (used for null patterns) and
`bool TryGetValue(out T value)` per case type (used for type patterns). Each is independently optional;
neither is a fallback for the other; without them the compiler falls back to `Value`.

Optional union member provider: a nested interface literally named `IUnionMembers` declaring static
`Create` methods (one per case type, return type identity-convertible to the union type), a `Value`
property, and optionally `TryGetValue`/`HasValue`. When present, only members declared on `IUnionMembers`
are used.

Behavioural assumptions the compiler makes about custom unions (soundness, stability, creation equivalence,
access pattern consistency) are stated in the language reference and are not checked.

Restrictions on `union` declarations: no instance fields, no auto-properties, no field-like events, and no
public single-parameter constructors (the compiler generates those).

**Down-level verdict**: `union` declarations compile for `netstandard2.0`, `net472` and `net8.0` provided
(a) `LangVersion` is raised to `15.0` or `preview` explicitly, and (b) the two types are polyfilled.
Nothing else in the lowering requires .NET 11. The generated struct is an ordinary struct with an
`object?` field.

Sources:
- https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/builtin-types/union
- https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/proposals/csharp-15.0/unions
- https://github.com/dotnet/roslyn/issues/81074
- https://github.com/dotnet/runtime/pull/127001

### 4.3 Closed hierarchies — `IsClosedTypeAttribute` and `CompilerFeatureRequiredAttribute`

The csharplang speclet's Lowering section, verbatim:

> Closed classes are generated with an `IsClosedType` attribute, to allow them to be recognized by a
> consuming compiler.
>
> ```cs
> namespace System.Runtime.CompilerServices
> {
>     [AttributeUsage(AttributeTargets.Class, AllowMultiple = false, Inherited = false)]
>     public sealed class IsClosedTypeAttribute : Attribute { }
> }
> ```
>
> #### Blocking subtyping from other languages/compilers
>
> Closed classes shall not be inherited from languages that do not support closed classes. This is
> accomplished by adding `[CompilerFeatureRequired("ClosedClasses")]` to all constructors of closed classes.
>
> Metadata "view" of `C1`:
>
> ```cs
> [IsClosedType]
> class C1
> {
>     [CompilerFeatureRequired("ClosedClasses")]
>     public C1() { }
>     [CompilerFeatureRequired("ClosedClasses")]
>     public C1(int param) { }
> }
> ```
>
> Note that unlike for the "required members" feature, an ObsoleteAttribute is not emitted in addition to
> the CompilerFeatureRequiredAttribute. Only the latter is emitted.

Multiple features stack, one attribute per required feature:

```cs
closed class C1
{
    public C() { }
    public required string P { get; set; }
}

// Metadata:
class C1
{
    [Obsolete("Types with required members are not supported in this version of your compiler")]
    [CompilerFeatureRequired("RequiredMembers")]
    [CompilerFeatureRequired("ClosedClasses")]
    public C1() { }
}
```

The error a down-level compiler reports when it sees the attribute:
`error: 'C1.C1()' requires compiler feature "ClosedClasses"`.

The runtime API proposal https://github.com/dotnet/runtime/issues/129009 (labelled `api-approved`)
extends the attribute:

```csharp
namespace System.Runtime.CompilerServices;

[AttributeUsage(AttributeTargets.Class, AllowMultiple = false, Inherited = false)]
public sealed class IsClosedTypeAttribute : Attribute
{
    public IsClosedTypeAttribute() { }
    public Type[] DerivedTypes { get; set; }
}
```

"The compiler will automatically populate this array with all direct derived type definitions within the
same module", emitted as `[IsClosedType(DerivedTypes = [typeof(Dog), typeof(Cat)])]`. System.Text.Json
consumes it: the reflection-based resolver and the source generator read `[IsClosedType].DerivedTypes`
and add one `JsonDerivedType` per applicable derived type, with a synthesized string discriminator of
`DerivedType.Name` (https://github.com/dotnet/runtime/issues/129041).

Note the csharplang speclet (as published on learn, commit `05eb4800`) still shows the *parameterless*
attribute with no `DerivedTypes`; the runtime issue is newer. Treat `DerivedTypes` as the shipping shape.

**Synthesis**: the Roslyn test plan (https://github.com/dotnet/roslyn/issues/81039) states
"An error is reported if ClosedAttribute is not found", and requires `CompilerFeatureRequiredAttribute`
to be "emitted on constructors of a closed class" and "not emitted on the closed class itself". Neither
attribute is synthesized.

**Down-level verdict for `closed`**: it needs *two* types that do not exist below `net7.0`
(`CompilerFeatureRequiredAttribute`) and below `net11.0` (`IsClosedTypeAttribute`). On `netstandard2.0`,
`netstandard2.1` and `net472` **both** must be polyfilled; on `net8.0`/`net10.0` only
`IsClosedTypeAttribute` must be. `CompilerFeatureRequiredAttribute` polyfilling is well-trodden
(this is the `CS0656` that `required` members produce on `net6.0`). `IsClosedTypeAttribute` polyfilling
is presumed to work by the same well-known-attribute rules but is **UNVERIFIED**. A polyfilled attribute
declared `internal` still round-trips correctly, because a consuming compiler matches the attribute by
full metadata name — the same way it reads compiler-embedded attributes.

Other semantics of `closed` that matter to a code model:
- `closed` is a contextual keyword and implies `abstract`; combining it with `sealed`, `static`, or an
  explicit `abstract` modifier is an error.
- Derivation is not transitive: a non-`closed` descendant of a `closed` class is still open.
- The same-assembly restriction is enforced at *module* granularity: "A subtype of a `closed` type must be
  located within the same module as the base type."
- If a generic class directly derives from a closed class, all its type parameters must appear in the base
  class specification (`class D3<W> : C<int>` is an error).
- A `closed` class with a *sealed hierarchy* (every subtype sealed or itself closed) gains an interface
  convertibility restriction: `(I)c` is an error when no member of the hierarchy implements `I`.
- A type parameter constrained to a closed class is treated as closed for exhaustiveness.
- An empty `switch` over a closed class with no subtypes is *not* exhaustive (documented "quirk").
- A subtype that is inaccessible or unconstructible at the use site does not contribute to exhaustiveness.

Sources:
- https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/proposals/csharp-15.0/closed-hierarchies
- https://github.com/dotnet/csharplang/blob/main/proposals/csharp-15.0/closed-hierarchies.md (champion issue csharplang#9499)
- https://github.com/dotnet/runtime/issues/129009
- https://github.com/dotnet/runtime/issues/129041
- https://github.com/dotnet/roslyn/issues/81039

### 4.4 `CompilerFeatureRequiredAttribute` in isolation

Declared in `System.Private.CoreLib` since **.NET 7**. Absent from `netstandard2.0`, `netstandard2.1`,
`net472`, `net6.0` and earlier. When a feature that emits it is used and the type is missing, the compiler
reports:

```
error CS0656: Missing compiler required member 'System.Runtime.CompilerServices.CompilerFeatureRequiredAttribute..ctor'
```

Hand-written polyfills are accepted; this is the standard workaround for `required` members on `net6.0`
and `netstandard2.0` (dotnet/core issue 8016, dotnet/csharplang discussion 6797, microsoft/CsWin32
issue 1146). Microsoft's position on `required` members specifically is that the polyfilled scenario
"is not officially supported", which is a support statement, not a compiler restriction.

C# 15 features that emit it: **closed classes** (feature name `"ClosedClasses"`).

Reference: https://learn.microsoft.com/en-us/dotnet/csharp/misc/cs0656

### 4.5 Memory safety — `MemorySafetyRulesAttribute` and `RequiresUnsafeAttribute`

From https://github.com/dotnet/csharplang/blob/main/proposals/unsafe-evolution.md:

```csharp
namespace System.Runtime.CompilerServices
{
    [AttributeUsage(AttributeTargets.Module, Inherited = false)]
    public sealed class MemorySafetyRulesAttribute : Attribute
    {
        public MemorySafetyRulesAttribute(int version) => Version = version;
        public int Version { get; }
    }
}
```

```csharp
namespace System.Runtime.CompilerServices
{
    [AttributeUsage(AttributeTargets.Event | AttributeTargets.Method |
                    AttributeTargets.Property | AttributeTargets.Constructor,
                    AllowMultiple = false, Inherited = false)]
    public sealed class RequiresUnsafeAttribute : Attribute
    {
    }
}
```

Key statements, verbatim from the speclet:

- "The `MemorySafetyRulesAttribute` and `RequiresUnsafeAttribute` definition is synthesized by the compiler
  if necessary per standard well-known member rules." → **the compiler embeds them**, so the feature is
  not gated on the target framework.
- "It is an error to apply the `MemorySafetyRulesAttribute` or `RequiresUnsafeAttribute` to any symbol
  explicitly in source." Use the `unsafe` modifier on the member instead; the attribute is for metadata only.
- "When a non-type member is marked as unsafe, the compiler will synthesize a `RequiresUnsafeAttribute`
  application on the member in metadata."
- "The compiler ignores `RequiresUnsafeAttribute`-marked members from assemblies that are using the legacy
  memory safety rules (instead, the compat mode is used there)."
- "When an assembly is compiled with the new memory safety rules, it gets marked with
  `MemorySafetyRulesAttribute`, filled in with 15 as the language version." (i.e. `Version = 15`.)
  This is exactly the shape of the existing `RefSafetyRulesAttribute(11)`.

**Namespace caveat.** The task brief called the attribute
`System.Diagnostics.CodeAnalysis.RequiresUnsafeAttribute`. The csharplang speclet places it in
`System.Runtime.CompilerServices`, and no `RequiresUnsafeAttribute` was found in the
`System.Diagnostics.CodeAnalysis` API listings. Treat `System.Runtime.CompilerServices` as the correct
namespace; the older dotnet/designs document
(https://github.com/dotnet/designs/blob/main/accepted/2025/memory-safety/caller-unsafe.md) shows a
different `AttributeUsage` (`Class | Struct | Method | Property | Constructor`) and states no namespace,
so it is superseded.

**Important sequencing note.** The .NET 11 documentation and the Roslyn breaking-change list place the
memory-safety pieces in different language versions, because the feature is being staged:

- "What's new in C# 15" says the pointer relaxations require `LangVersion` = `preview` and
  `AllowUnsafeBlocks`, and that "the *requires-unsafe* member model and the assembly opt-in to the updated
  memory safety rules aren't available yet, so `safe` and `unsafe` currently have no effect on callers."
- The Roslyn breaking-change document attributes "Pointer types no longer require an unsafe context"
  (VS 18.7), "`safe` is a contextual keyword" (VS 18.9) and "`unsafe` required for more members"
  (VS 18.9, `CS9363`, `langversion:16`) to **C# 16**.

So at .NET 11 GA the memory-safety model is expected to be **preview-only**, driven by
`LangVersion=preview`, not by `net11.0`. The dotnet/designs document mentions an `EnableRequiresUnsafe`
compilation property; **the final MSBuild property name is UNVERIFIED**.

Relaxations available in C# 15 with `LangVersion=preview` (no `unsafe` context needed):
- declaring a pointer type and taking an address with `&`;
- the `fixed` statement;
- converting a `stackalloc` expression to a pointer;
- `sizeof` on any unmanaged type.

Still requiring `unsafe`: pointer indirection (`*p`), pointer member access (`p->m`), pointer element
access (`p[i]`), function pointer invocation.

New `unsafe(expression)` form, for places where an `unsafe` block cannot appear (field initializers,
constructor initializers, `catch` filters):

```csharp
class Header
{
    // A field initializer can't contain an unsafe block, but it can contain an unsafe expression.
    static readonly int Signature = unsafe(ReadSignature());

    static unsafe int ReadSignature()
    {
        int rawValue = 0x1234;
        int* pointer = &rawValue;
        return *pointer;
    }
}
```

The `safe` contextual keyword is recognized as a modifier on `extern` members and explicit-layout fields
but currently has no effect on callers.

Sources:
- https://github.com/dotnet/csharplang/blob/main/proposals/unsafe-evolution.md
- https://github.com/dotnet/csharplang/issues/9704
- https://github.com/dotnet/roslyn/issues/81207 (test plan)
- https://github.com/dotnet/roslyn/pull/82547 (merge to main)
- https://learn.microsoft.com/en-us/dotnet/csharp/whats-new/csharp-15#memory-safety

### 4.6 `CollectionBuilderAttribute` under the relaxed C# 15 create-method rules

`System.Runtime.CompilerServices.CollectionBuilderAttribute` shipped in **.NET 8**. It is not synthesized;
it is routinely polyfilled in source (both Meziantou.Polyfill and SimonCropp/Polyfill ship it).

The C# 15 relaxation, verbatim from the collection-expression-arguments speclet:

> First, the set of applicable *create methods* `CM` is determined. It consists of methods that meet the
> following requirements:
> - The method must have the name specified in the `[CollectionBuilder(...)]` attribute.
> - The method must be defined on the *builder type* directly.
> - The method must be `static`.
> - The method must be accessible where the collection expression is used.
> - The *arity* of the method must match the *arity* of the collection type.
> - The method must have a **last** parameter of type `System.ReadOnlySpan<E>`, passed by value.
> - There is an identity conversion, implicit reference conversion, or boxing conversion from the method
>   return type to the *collection type*.
>
> Methods declared on base types or interfaces are ignored and not part of the `CM` set.

> The key differences from the earlier algorithm are:
> - Create methods may have additional parameters *before* the `ReadOnlySpan<E>` parameter.
> - Multiple create methods are supported.

The builder type "must be a non-generic `class` or `struct`". Overload resolution uses *projection methods*
— the create method minus its last parameter — matched against the `with(...)` argument list; the chosen
create method is then invoked with the argument list plus the `ReadOnlySpan<T>` of elements.

```csharp
[CollectionBuilder(typeof(MyBuilder), "Create")]
class MyCollection<T> { ... }

class MyBuilder
{
    public static MyCollection<T> Create<T>(ReadOnlySpan<T> elements);
    public static MyCollection<T> Create<T>(IEqualityComparer<T> comparer, ReadOnlySpan<T> elements);
}

MyCollection<string> c1 = [with(GetComparer()), "1", "2"];
// IEqualityComparer<string> _tmp1 = GetComparer();
// ReadOnlySpan<string> _tmp2 = ["1", "2"];
// c1 = MyBuilder.Create<string>(_tmp1, _tmp2);

MyCollection<string> c2 = [with(), "1", "2"];
// ReadOnlySpan<string> _tmp3 = ["1", "2"];
// c2 = MyBuilder.Create<string>(_tmp3);
```

Other rules that matter to a rewriter:
- If `with(...)` is present and is not the first element, a compile-time error is reported.
- `dynamic` arguments in `with(...)` are disallowed (LDM 2025-01-22).
- Collection arguments are ignored for conversion and type inference (LDM 2025-03-17).
- `__arglist` is not supported in collection arguments (LDM 2025-04-14).
- Arrays and spans reject `with()` entirely: `Span<int> a = [with(), 1, 2, 3];` and
  `int[] b = [with(length: 1), 3];` are errors.
- Convertibility now depends on the *presence* of a `with_element`, not on its arguments: with a
  `with_element` the type needs "at least one constructor accessible at the location of the collection
  expression"; without one it still needs a parameterless constructor.
- Interface target types accept a curated argument set: `()` for `IEnumerable<E>`/`IReadOnlyCollection<E>`/
  `IReadOnlyList<E>`; `List<E>()` and `List<E>(int)` for `ICollection<E>`/`IList<E>`;
  `Dictionary<K,V>()`, `(int)`, `(IEqualityComparer<K>)`, `(int, IEqualityComparer<K>)` for `IDictionary<K,V>`;
  `()` and `(IEqualityComparer<K>? comparer)` for `IReadOnlyDictionary<K,V>`.
- Ref safety: for a create method, safe-context is computed as an invocation whose arguments are the
  `with()` arguments followed by the collection expression as the last (`ReadOnlySpan<E>`) argument.

Parsing rule with a compatibility consequence:
"if the element lexically starts with the token sequence `with` `(` then it is always treated as a
`with_element`". Escape with `@with` to call a method named `with`. The break is language-version gated
(LDM 2025-03-17), and the breaking-change list records it as
"`with()` as a collection expression element is treated as collection construction *arguments*", introduced
in VS 18.4, active "when the LangVersion is set to 15 or greater".

Also note the separate, *not* language-version-gated break from VS 18.3:
"The *safe-context* of a collection expression of Span/ReadOnlySpan type is now *declaration-block*"
(previously *function-member*).

**Down-level verdict**: the relaxed create-method rules are `LangVersion`-gated, not TFM-gated, and
`CollectionBuilderAttribute` is polyfillable. A `netstandard2.0` build with `LangVersion=15.0` and a
polyfilled attribute can use them; `ReadOnlySpan<T>` must come from the `System.Memory` package.

Source: https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/proposals/csharp-15.0/collection-expression-arguments
(champion issue csharplang#8887)

### 4.7 `System.Runtime.InteropServices.InAttribute` — newly required

Two separate entries in the Roslyn breaking-change document, both "Introduced in Visual Studio 2026
version 18.3", both reporting the same diagnostic.

> ## Scenarios requiring compiler to synthesize a `ref readonly` returning delegate now require
> availability of `System.Runtime.InteropServices.InAttribute` type.
>
> The C# compiler made a breaking change in order to properly emit metadata for `ref readonly` returning
> synthesized delegates.
>
> This can cause an "error CS0518: Predefined type 'System.Runtime.InteropServices.InAttribute' is not
> defined or imported" to appear in existing code, such as in the scenarios below:
>
> ```cs
> var d = this.MethodWithRefReadonlyReturn;
> ```
> ```cs
> var d = ref readonly int () => ref x;
> ```
>
> If your code is impacted by this breaking change, consider adding a reference to an assembly defining
> `System.Runtime.InteropServices.InAttribute` to your project.

> ## Scenarios utilizing `ref readonly` local functions now require availability of
> `System.Runtime.InteropServices.InAttribute` type.
>
> ```cs
> void Method()
> {
>     ...
>     ref readonly int local() => ref x;
>     ...
> }
> ```

The diagnostic is **`CS0518`**, not `CS0656`. `InAttribute` is present in `mscorlib` (.NET Framework),
`netstandard.dll` (netstandard2.0 and 2.1) and every `System.Runtime` since .NET Core, so in ordinary
multi-targeting this break is inert. It bites in compilations with a hand-assembled or trimmed reference
set — which is the situation for compiler-hosted test compilations that reference only a minimal corlib,
and for source generators or analyzers that build a `CSharpCompilation` from a curated
`MetadataReference` list. Because it is a `CS0518` predefined-type lookup, declaring the type in source
satisfies it.

Source: https://learn.microsoft.com/en-us/dotnet/csharp/whats-new/breaking-changes/compiler%20breaking%20changes%20-%20dotnet%2011

### 4.8 `System.Runtime.InteropServices.ExtendedLayoutAttribute`

Roslyn feature status lists "ExtendedLayoutAttribute — main — Merged into 18.3". From the .NET 11
Preview 1 C# release notes and `roslyn/docs/features/ExtendedLayoutAttribute.md`:

- "The C# compiler emits the `TypeAttributes.ExtendedLayout` for types that have the
  `System.Runtime.InteropServices.ExtendedLayoutAttribute` applied."
- "When `System.Runtime.InteropServices.ExtendedLayoutAttribute` is applied to a type definition, the
  `System.Runtime.InteropServices.StructLayoutAttribute` pseudo-attribute is considered applied and the
  `layoutKind` is set to 1."
- "The `Layout` property will return a `TypeLayout` instance with the `LayoutKind` set to `Extended` (`1`),

- The compiler prevents applying `StructLayoutAttribute` to a decorated type, and (C# only) prevents

- The attribute is preserved on types embedded via NoPia.

An API documentation page exists at
https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.extendedlayoutattribute?view=net-11.0,

**UNVERIFIED**: the diagnostic identifiers for the `StructLayout`/`InlineArray` conflicts, and whether a

### 4.9 `System.Runtime.CompilerServices.AsyncHelpers` and runtime async

- .NET 11 ships "Runtime Async V2". Opt in per project with
  `<Features>runtime-async=on</Features>`; opt out with `<UseRuntimeAsync>false</UseRuntimeAsync>`.
- "A `net11.0` project no longer requires `<EnablePreviewFeatures>true</EnablePreviewFeatures>` to use
  Runtime Async."
- The `DOTNET_RuntimeAsync` and `UNSUPPORTED_RuntimeAsync` environment variables **have been removed**.
- The runtime libraries themselves are compiled with `runtime-async=on` and "no longer contain
  compiler-generated state machines and rely entirely on runtime-provided async".
- `System.Runtime.CompilerServices.AsyncHelpers` provides static helpers marked
  `[MethodImpl(MethodImplOptions.Async)]`: `AwaitAwaiter`, `UnsafeAwaitAwaiter`, and `Await` overloads for
  the various task types. `MethodImplOptions.Async` is the metadata marker for a runtime-async method.
  `[RequiresPreviewFeatures]` was removed from the runtime-async API surface
  (https://github.com/dotnet/runtime/pull/124488).
- **Metadata consequence**: with runtime async an `async` method emits **no state-machine type** and no
  `AsyncStateMachineAttribute`; the method itself carries `MethodImplOptions.Async`. Live stack traces
  collapse from 13 frames to 5 in the documented example. Anything that inspects IL, walks state machines,
  or rewrites `async` bodies must handle both shapes.
- Runtime async supports NativeAOT and ReadyToRun in .NET 11; crossgen2 inlining restrictions were removed;
  covariant `Task` to `Task<T>` overrides now work via a generated void-returning thunk.
- Roslyn's feature list also has "Runtime Async Streams — features/runtime-async-streams — Test plan active
  — not merged to main", so `IAsyncEnumerable` is not yet covered.
- The async profiler now instruments both runtime-async methods and compiler-generated state-machine
  methods so tools receive one consistent event model.

**Down-level verdict**: runtime async requires the .NET 11 runtime. It is not available on
`netstandard2.0`, `net472`, `net8.0` or `net10.0` under any polyfill.

Sources:
- https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-11/runtime#runtime-async
- https://github.com/dotnet/runtime/blob/main/docs/design/specs/runtime-async.md
- https://github.com/dotnet/runtime/issues/114310
- https://learn.microsoft.com/en-us/dotnet/api/system.runtime.compilerservices.asynchelpers

### 4.10 Features with no framework-type dependency

| Feature | Requires | Down-level |
|---|---|---|
| Labeled `break` / `continue` | nothing | works on any TFM with `LangVersion >= 15` |
| Extension indexers | `ExtensionAttribute` and `DefaultMemberAttribute` (both in `netstandard2.0`), plus the compiler-synthesized `ExtensionMarkerNameAttribute` and grouping/marker types | works on any TFM with `LangVersion >= 15` |
| Collection expression `with(...)` on constructors and interface targets | `List<T>` / `Dictionary<K,V>` constructors already present | works down-level |
| Non-virtual static interface members | **UNVERIFIED** | **UNVERIFIED** |

Labeled `break`/`continue` syntax, for the record:

```csharp
outer: for (int row = 0; row < grid.Height; row++)
{
    for (int column = 0; column < grid.Width; column++)
    {
        if (grid[row, column].IsBlocked) { continue outer; }
        if (grid[row, column].IsGoal)    { break outer; }
    }
}
```

The label is placed directly on the loop or `switch` it identifies. `IDE0410` flags the patterns it replaces.

Extension indexer lowering, verbatim from the speclet:

```csharp
[Extension]
static class BitExtensions
{
    [Extension, SpecialName, DefaultMember("Item")]
    public sealed class <G>$T0 // grouping type
    {
        [SpecialName]
        public static class <M>$T_t // marker type
        {
            [SpecialName]
            public static void <Extension>$(T t) { } // marker method
        }

        [ExtensionMarkerName("<M>$T_t")]
        public bool this[int index] // extension indexer
        {
            get => throw new NotImplementedException();
            set => throw new NotImplementedException();
        }
    }

    // accessor implementation methods
    public static bool get_Item<T>(T t, int index) => ...;
    public static void set_Item<T>(T t, int index, bool value) => ...;
}
```

`[DefaultMemberAttribute]` is emitted on any extension grouping type that contains one or more extension
indexers. `IndexerNameAttribute` may be applied to an extension indexer, is *not* emitted in metadata, but
determines the metadata name of the property and accessors and the `DefaultMember` value.
CREF syntax: `<see cref="E.extension(int).this[string]"/>`, `<see cref="E.extension(int).get_Item(string)"/>`,
`<see cref="E.set_Item(int, string, int)"/>`.
Extension indexers cannot appear in expression trees, and do not apply to arrays or strings
(LDM 2026-04-07). Lookup order (LDM 2026-03-09): real instance indexers, then implicit instance indexers,
then real extension indexers, then implicit extension indexers. Extension `Length`/`Count` and extension
`Slice` do contribute to countability and the implicit-indexer fallback, but extension `Length` does not
contribute to the spread-optimization size hint.

Source: https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/proposals/csharp-15.0/extension-indexers
(champion issue csharplang#9856)

## 5. Multi-targeting with `netstandard2.0` in the same build

### 5.1 What is per-TFM and what is per-project

| Setting | Scope |
|---|---|
| `LangVersion` (default) | **per-TFM** — `15.0` on `net11.0`, `7.3` on `netstandard2.0`/`net472`, `12.0` on `net8.0`, `14.0` on `net10.0` |
| Preprocessor symbols | per-TFM |
| Implicit usings set | per-TFM (the `System.Net.Http.Json` entry is conditioned on `TargetFrameworkVersion >= 11.0`) |
| `AnalysisLevel`, `EffectiveAnalysisLevel`, `WarningLevel` | per-TFM |
| `EnableNETAnalyzers` | per-TFM (true only when `EffectiveAnalysisLevel >= 5.0`, i.e. never for `netstandard2.0`/`net472`) |
| `ProduceReferenceAssembly` | per-TFM (true only for `.NETCoreApp >= 5.0`) |
| Reference set (shared framework contents) | per-TFM |
| `SdkAnalysisLevel` | **per-project / per-SDK**, not per-TFM |
| NuGet restore, pruning, NU1510 | per-TFM restore, but NU1510 is raised only when pruning applies to **all** runtime targets |

The immediate practical consequence: a multi-targeted library that wants C# 15 syntax anywhere must set
`LangVersion` explicitly, because the default is `7.3` on `netstandard2.0` and `net472`. Setting
`<LangVersion>15.0</LangVersion>` globally is legal but Microsoft documents it as unsupported:
"Using a C# language version newer than the version associated with your target TFM isn't supported."
It nonetheless works for every construct that does not need a missing framework type, which is precisely
what the table in section 4.1 enumerates.

### 5.2 NuGet asset selection and NU1510

`PrunePackageReference` has been on by default since .NET 10 for projects targeting .NET 10 or higher.
Under .NET 11 the nine `Microsoft.Extensions.*` packages join the prunable set for `net11.0`.

The rule that governs a multi-targeted build, verbatim from the NU1510 page:

> Beginning with .NET 10, the `PrunePackageReference` feature is enabled by default for all projects that
> target .NET 10 or higher. **The warning is only raised when pruning applies to all runtime targets**:
>
> ```xml
>   <PropertyGroup>
>     <!-- 'System.Text.Json' is not SDK-bundled in 'net48' -->
>     <TargetFrameworks>net10.0;net48</TargetFrameworks>
>   </PropertyGroup>
>
>   <ItemGroup>
>     <!-- This reference is needed in 'net48' - NU1510 is not raised -->
>     <PackageReference Include="System.Text.Json" Version="9.0.7" />
>   </ItemGroup>
> ```

And from the breaking-change page:

> For multi-targeted projects (for example, `<TargetFrameworks>net10.0;net11.0</TargetFrameworks>`),
> NU1510 isn't raised because the package is still required for the older TFM. No action is required —
> NuGet selects the appropriate assembly for each target framework automatically.

**So a library targeting `netstandard2.0;net472;net8.0;net10.0;net11.0` that references, say,
`Microsoft.Extensions.Logging.Abstractions` will NOT get NU1510.** The warning appears only for a project
that targets `net11.0` (or a set of TFMs all of which bundle the package) exclusively.

What *does* change on the `net11.0` leg regardless of NU1510: build-time conflict resolution picks the
shared-framework assembly over the package assembly, and the package assembly is no longer copied to the
output folder. If the referenced package version is older than the .NET 11 version, that leg silently
compiles and runs against the newer API surface. Downstream binaries built against the older reference are
where the `MissingMethodException` / `TypeLoadException` risk quoted in section 3.2 materialises.

The optional explicit form given by the documentation:

```xml
<!-- Keep the reference only for TFMs that don't include it in the shared framework: -->
<PackageReference Include="Microsoft.Extensions.Logging.Abstractions" Version="..." Condition="'$(TargetFramework)' != 'net11.0'" />
```

The second NU1510 scenario is relevant to a multi-project repository: pruning uses the *direct*
`FrameworkReference` items of the current project only. A project that inherits a framework reference
transitively through a `ProjectReference` does not prune, so it restores the package and relies on
build-time conflict resolution instead. Adding the matching `FrameworkReference` directly restores pruning
and surfaces NU1510.

Sources:
- https://learn.microsoft.com/en-us/nuget/reference/errors-and-warnings/nu1510
- https://learn.microsoft.com/en-us/dotnet/core/compatibility/extensions/11/extensions-in-shared-framework
- https://learn.microsoft.com/en-us/dotnet/core/compatibility/sdk/10.0/nu1510-pruned-references

### 5.3 Other multi-targeting consequences

- **Template engine packages no longer support `netstandard2.0`** (breaking change
  `sdk/11/template-engine-netstandard`, classified binary/source incompatible). Anything that consumed
  `Microsoft.TemplateEngine.*` from a `netstandard2.0` assembly must move up.
- **VSTest removes its dependency on `Newtonsoft.Json`** (`sdk/11/vstest-removes-newtonsoft-json`,

  `-p:ContinuousIntegrationBuild=True` this is where new warnings first appear.

### 6.1 Roll-forward

No change was found for .NET 11. The mechanism, verbatim from the installed SDK

### 6.2 Runtime selection: the raised hardware baseline

Targeting `net11.0` implies the .NET 11 **runtime**, whose minimum hardware requirements were raised.
This is the practical runtime-selection consequence of the TFM.

x86/x64, all three operating systems — baseline moves `x86-64-v1` to **`x86-64-v2`**:

| OS | Previous JIT/AOT minimum | New JIT/AOT minimum | Previous R2R target | New R2R target |
|---|---|---|---|---|
| Apple | x86-64-v1 | x86-64-v2 | x86-64-v2 | (no change) |
| Linux | x86-64-v1 | x86-64-v2 | x86-64-v2 | **x86-64-v3** |
| Windows | x86-64-v1 | x86-64-v2 | x86-64-v2 | **x86-64-v3** |

`x86-64-v2` adds guaranteed `CX16`, `POPCNT`, `SSE3`, `SSSE3`, `SSE4.1`, `SSE4.2` on top of
`CMOV`, `CX8`, `SSE`, `SSE2`. `x86-64-v3` additionally includes `AVX`, `AVX2`, `BMI1`, `BMI2`, `F16C`,
`FMA`, `LZCNT`, `MOVBE`.

Arm64:

| OS | Previous JIT/AOT minimum | New JIT/AOT minimum | Previous R2R target | New R2R target |
|---|---|---|---|---|
| Apple | Apple M1 | (no change) | Apple M1 | (no change) |
| Linux | armv8.0-a | (no change) | armv8.0-a | armv8.0-a + LSE |
| Windows | armv8.0-a | armv8.0-a + LSE | armv8.0-a | armv8.2-a + RCPC |

Failure mode on unsupported hardware:
"The current CPU is missing one or more of the baseline instruction sets."

## 9. Practical checklist for a multi-targeted library that wants C# 15

1. Set `<LangVersion>15.0</LangVersion>` explicitly (project-wide or per-TFM). Without it, `netstandard2.0`
   and `net472` get `7.3`.
2. If you use `union`: polyfill `System.Runtime.CompilerServices.UnionAttribute` and `IUnion` for every TFM
   below `net11.0`. Guard the polyfill with `#if !NET11_0_OR_GREATER`.
3. If you use `closed`: polyfill `System.Runtime.CompilerServices.IsClosedTypeAttribute` for every TFM below
   `net11.0`, **and** `System.Runtime.CompilerServices.CompilerFeatureRequiredAttribute` for every TFM below
   `net7.0`. (`IsClosedTypeAttribute` polyfill acceptance is UNVERIFIED.)
4. If you use the relaxed `[CollectionBuilder]` create-method shapes: polyfill
   `System.Runtime.CompilerServices.CollectionBuilderAttribute` below `net8.0` and reference `System.Memory`
   for `ReadOnlySpan<T>`.
5. Do not expect `ExtendedLayoutAttribute` or runtime async to work below `net11.0`.
6. `MemorySafetyRulesAttribute` / `RequiresUnsafeAttribute` need no polyfill (the compiler embeds them), but
   never apply them in source; and the surrounding feature needs `LangVersion=preview` (C# 16 territory).
7. Expect a stricter `net11.0` leg: warning wave 11, `AnalysisLevel=latest` meaning .NET 11 rules
   (and, because of the `latest`-resolves-to-.NET-9 bug fix, two releases of new default-on rules at once).
8. Expect a wider `net11.0` reference set: nine `Microsoft.Extensions.*` assemblies plus an implicit
   `global using System.Net.Http.Json`. Resolve any new ambiguity with explicit usings or aliases.
9. Do **not** expect NU1510 for `Microsoft.Extensions.*` package references in a build that also targets
   `netstandard2.0`; it is suppressed because pruning does not apply to all runtime targets.
10. Verify with `#error version` (reports `CS8304` with the compiler and selected language version) per TFM
    if the effective `LangVersion` is ever in doubt.

> Part of the [call-site interceptors design](README.md). Previous: [appendix-c-review-log.md](appendix-c-review-log.md). Evidence prefixes and terms: [00-conventions.md](00-conventions.md).

## Appendix D. Product-owner reviews of 2026-09-24 and 2026-09-25

The product owner reviewed the design on 2026-09-24, after the review of [Appendix C](appendix-c-review-log.md#appendix-c-review-log), and sent a third, a fourth, a fifth and a sixth batch of decisions on 2026-09-25. This appendix records the decisions of that review. They supersede any earlier text of this document that conflicts with them.

Decisions applied before this review:

- The verb for method targets is `InterceptMethods`, with `IMethodInterceptor`, `MethodInterceptionContext` and the template accessor `MethodInterception`. It replaces `InterceptInvocations` (RC34).
- The kind of method use is the flags enumeration `MethodInterceptionKinds`. Version 1 has only `Call`. `Delegate` is deferred and opt-in. The enumeration has no `All` member, and the default value never grows (section [5.3.11](05a-api-registration.md#5311-kinds-of-method-use), PO44). The second product-owner batch reversed this decision (D-S, RC44).

Discrepancies between the decisions of the batch and verified facts, resolved by the closest correct version:

- Function pointers: the batch stated that function-pointer conversions allow no implicit conversions. Roslyn applies the rules of delegates to function pointers: identity or implicit reference conversions for parameters and the return type, plus pointer conversions (RC `Binder\Binder_Conversions.cs:3516-3659`). The design keeps the requirement of an identical signature, for the reason of section [6.4.12](06b-signatures-and-validation.md#6412-method-reference-sites), which applies to every method-reference site.
- Null receivers: the batch assumed that a method-group shape keeps the moment of the exception. Under R1x, a delegate closed over a null receiver is created without an exception, so the exception moves to the invocation. This is documented as the method-reference form of PO17 (section [6.4.12](06b-signatures-and-validation.md#6412-method-reference-sites)).
- Milestones: the batch placed method references of static targets in M2 and the R2 and R1x shapes in M3. The design places existing static methods at method-reference sites in M1, with `RedirectMethodReference` in M0, so that the first prerelease never intercepts the lambda form of a static call without the method-group form; synthesized interceptors and R1x in M2, where R1x already ships for calls; R2, R4 and the wrapper in M3; local functions in M4.

Discrepancies between the decisions of the third batch and verified facts, resolved by the closest correct version:

- `init` accessors: the batch stated that their only use sites are object and `with` initializers. C# also lets a constructor or an `init` accessor of the declaring type or of a derived type assign an `init` property on `this` or `base` (RC `Binder\Binder.ValueChecks.cs:2180-2205`). An interceptor method is neither, so no `init` site can be rewritten, and every `init` site gets the limitation `InitOnlySetter` (section [6.2.11](06a-call-site-model.md#6211-accessor-sites)).
- Positions that refuse pattern variables: the batch asked to list them, for example field initializers, constructor initializers, attribute arguments, `for` incrementors and query clauses. The errors that refused expression variables in field initializers, constructor initializers and query clauses are commented out in the Roslyn fork (RC `Errors\ErrorCode.cs:1467-1468`), and a compiled test accepted all these positions. Attribute arguments are constants. The only restriction found is syntactic: a conditional expression is not a statement expression, so a `for` incrementor or a `void` lambda body needs the discard form `_ = ...` (section [6.4.13](06b-signatures-and-validation.md#6413-accessor-sites)).
- "Every await" as a `null` argument: a `null` literal converts to `Type`, to `INamedType` and to the delegate type, so the call would be ambiguous (CS0121). Every await is selected by the overload without an awaitable type (section [5.3.4](05a-api-registration.md#534-await-registrations)).
- Struct receivers in expression contexts: a pattern variable copies a struct, so a compound site whose struct receiver is a variable with side effects cannot be rewritten in an expression, where a `ref` local cannot be declared. It gets `ReceiverTemporaryNotPossible`. In a statement, the rewrite uses a `ref` local where C# allows one.
- The one-source rule: the batch states that overlapping registrations of the same source count once. The source was one registration call; it is now the registering aspect instance or fabric instance, and the first non-skip result in registration order applies (section [9.5.8](09-premium-engine.md#958-conflict-detection-r7-b7)). The earlier test that expected LAMA1010 for two registrations of one aspect on one target now expects one interception ([Appendix B](appendix-b-weak-spots.md#appendix-b-weak-spots-that-remain-after-the-review), item 37).
- `IsChecked` for a site without an operator (a plain read or write, an event subscription) is `false`, because the public operation model exposes the checked context only on operators (`ICompoundAssignmentOperation.IsChecked`, `IIncrementOrDecrementOperation.IsChecked`).

Choices made by the lead while applying the fourth batch:

- The destination of an accessor site is the property or the event, as the destination of a reference to a property in reference validation. The accessor is `InterceptedMethod`, and its definition is the definition of `InterceptedMethod`. The batch described the destination as the bound method or accessor definition. For a use of an ordinary method, both readings give the same member.
- The destination of an await site is `AwaitableType`, and no `Destination` property is added to `AwaitInterceptionContext`. The value would be the same, and the base class cannot declare one `Destination` property with an `IMember` type for member sites and an `IType` type for await sites.
- `CallingMember` of the context is removed and not renamed, because `Origin` gives the same member. `CallingMember` of the meta extensions becomes `Origin`, because a local function is always declared in the origin of the sites that call it. `CallingType` and `CallingNamespace` stay, because `InterceptorPlacement.CallingType()` uses the same term.
- The word origin already named the contribution origin (`ExtensionContributionOrigin`) and the root of a query. The document now writes "contribution origin" and "query root" for these concepts, and the source column of the interpretation table is named Source.

Choices made by the lead while applying the fifth batch, and discrepancies with verified facts:

- `AwaitInterceptionOptions` stays a record with the single property `Scope`, rather than being replaced by the flags enumeration `InterceptionScopeOptions`. A record can receive a later option without a new overload, and the await verb keeps the parameter shape of the member verbs.
- The batch removes `AwaitableKinds`. The context still needs the kind of one await, which earlier versions expressed as `AwaitableKinds` with exactly one flag set. The design adds the non-flags enumeration `AwaitableKind` for the context and for `AwaitInterceptionInfo`. This reverses the merge of review finding API-09, whose reason, one enumeration for the filter and the kind, no longer exists.
- The batch lists an existing-method shorthand among the await forms. The design never had one, and none is added. Without a type filter, one existing method would be validated against every await of the scope, and each await whose type it does not accept would report LAMA1013. A provider returns `InterceptorResult.ExistingMethod` after it tests the awaitable type (sample 10b).
- The batch states that removing the type filter does not change the cost. The binding cost does not change, because the index never filtered awaits by name. The site analysis of section [7.2](07-await-interception.md#72-site-analysis) and the provider call now also run for the awaits that a type filter discarded before the analysis. Both run on bodies that the index has already bound (sections [5.3.4](05a-api-registration.md#534-await-registrations) and [9.6](09-premium-engine.md#96-cost-model-and-shared-binding)).
- `MethodTemplateSelector` is declared in `Advising\MethodTemplateSelector.cs` of FW27, not in `Aspects`. Its implicit conversion from `string` is at line 174. With a `string` overload of `InterceptorResult.Template`, C# prefers the identity conversion (RC `Binder\Semantics\OverloadResolution\OverloadResolution.cs:3003-3004`), so a template name never becomes a selector, and the existing calls with a template name keep their meaning at method sites.
- For override templates, `Task<dynamic>` is a wildcard that keeps the return type of the target (ENG27 `Advising\TemplateBindingHelper.cs:803-812`). For await interceptors, the batch makes `async Task<dynamic?>` select `Task<R>`. The design applies the batch, because an interceptor has no return type to keep. The documentation states the difference: the usual `async Task<dynamic?>` template gives `Task<R>`, not the default `ValueTask<R>` of a non-async template.
- The engine keeps passing a `MethodTemplateSelector` to the open-source factory for await interceptors. The engine builds it from the template name, with no alternative template and with `UseAsyncTemplateForAnyAwaitable` in mode `Await`. This selector is internal. It lets a non-async template produce an `async` interceptor with the existing selection helper (ENG27 `Advising\AdviceFactory.cs:262`; `Advising\TemplateExtensions.cs:113-115`), so the helper needs no change.
- Stage 1 needs the `async` modifier and the declared return type of an await template to compute `T_I` and the key. The design adds the open-source helper `ExtensionTemplateServices.TryGetMethodTemplateShape` (section [10.6.1](10b-oss-linker-and-templates.md#1061-selection-at-declaration-time)), which is new public API of the engine (PO2).
- The batch asks for a clear error when a template placed with `BaseMostAccessibleType()` needs a member of the calling type. The design finds no point before the compilation of the generated code where the engine could detect it, because member accesses on `meta.This` are run-time code that the template compiler emits without binding. The C# compiler reports the error ([Appendix B](appendix-b-weak-spots.md#appendix-b-weak-spots-that-remain-after-the-review), item 38, risk T37).
- The batch describes the result of the walk as the base-most type for which every check passes. The design stops the walk at the first failing type, so that the selected type is always reached through admissible types. The two definitions differ when a check fails for a type and passes for a type above it. The access checks and the naming checks do not produce this case. The hidden-target check can produce it, when an intermediate type declares a member that hides the target. The design then keeps the type below the hiding type, which is admissible and deterministic.
- The protected rule of `BaseMostAccessibleType()` was verified against Roslyn: a protected instance member is accessible through a receiver whose type derives from the accessing type (RC `Binder\Semantics\AccessCheck.cs:475`). The original call in the calling type `C` already satisfied the rule for `C`, and `C` derives from the selected type, so the proceed call through a receiver parameter of the selected type is valid.
- The batch asks for a test in which the walk stops at a generic base. A generic base type reached through inheritance passes check C6, and section [6.4.6](06b-signatures-and-validation.md#646-generic-specialization-and-lifting) lifts the types that it cannot name, so the walk continues. The walk stops below a base type that is nested in a generic type that the calling type does not inherit (check C6). The tests cover both cases.

Choices made by the lead while applying the sixth batch, and discrepancies with verified facts:

- Receiver-mapping overrides. The batch lists the permitted overrides R2 to R3, R2 to R1 and R3 to R1. The design also keeps R1 to R3 and the instance choice of R0 through `IsStatic = false`, because R13 requires an instance interceptor in the calling hierarchy, and sample 6, sample B of the overview and example 5 of section [6.4.3](06b-signatures-and-validation.md#643-worked-examples-of-the-receiver-mapping) use it. R0 and R4 stay fixed as mappings.
- `IInterceptorParameterBinder.Argument` is nullable. The batch declares it non-nullable, but no source represents the declared default of an optional parameter of an existing method, or an unbound required parameter. The value is `null` in these two cases.
- The binder keeps `InterceptedMethod`, and the builder keeps a `ReturnType` setter. The batch does not list them, but they are members of the earlier builder that remain valid.
- The `params` example. The batch rewrites `M( a, 1, 2 )`, against `M( A a, int b = 5, params int[] xs )`, as `I( r, a, 5, [1, 2], cancellationToken: ct )`. C# binds a positional argument to an optional parameter before a `params` element (RC `Binder\Semantics\OverloadResolution\OverloadResolution_ArgsToParameters.cs:271-302`, section [6.4.4](06b-signatures-and-validation.md#644-defaults-and-params), rule c), so `b` is `1` and `xs` is `[2]`. The design writes `I( r, a, 1, [2], cancellationToken: ct )`, and shows the materialized default with `r.M( a )`, which becomes `I( r, a, 5, [], cancellationToken: ct )`.
- The binding example. The batch declares `static void Track( string operation, Order target, bool withTax )` for the site `order.Total( true )`, whose value is used. A `void` method cannot intercept a call whose value is used (E14), so `Track` returns `decimal`.
- Pulled parameters. `PullAction.UseExistingParameter( p )` stores only `ExpressionFactory.Parse( p.Name )`, and the kind of a pull action is internal (FW27 `Advising\PullAction.cs:42, 119`). An extension cannot tell a pulled parameter from a parsed name, nor `IntroduceParameterAndPull` from `None`. The design adds the open-source change E3 (section [10.9](10c-oss-reference-graph-design-time.md#109-small-public-helpers-b2g)): a public kind and a public parameter.
- LAMA1018. The batch states that the premium self-interception rule LAMA1018 targets synthesized interceptors. In this design, LAMA1018 is rule E17, which applies to existing methods, and E2 refuses an existing method that is the target. Neither rule belongs to the factory, which accepts a redirection that keeps the original target (section [10.4.5](10a-oss-bridge-hook-factory.md#1045-call-site-redirections)).
- `CallerInstance` is also unavailable in lambdas and local functions of struct members, because C# forbids capturing `this` of a struct (CS1673). Its availability is exactly `InterceptionContext.CanAccessThis`.
- Mode `Awaitable` with `AnyAwaitable<dynamic?>`. The batch gives the interceptor the type of the returned expression. Stage 1 needs `T_I` for the key before any expansion, so `T_I` stays the type passed to `WithAwaitRewriteOptions`, or `A`. A pass-through returns `A`, as the batch states.
- The exemption of `dynamic` as a type argument (LAMA0227) was verified: the list is matched by name and does not contain `AnyAwaitable` (ENG27 `CompileTime\SymbolClassifier.cs:620-636`), so `AnyAwaitable` must be added. The open point of the batch is therefore a required change.
- A result-bearing template on a target whose result is `void` was verified: the expander emits the returned expression as a statement and a bare `return` (ENG27 `Templating\TemplateExpansionContext.cs:393-407, 606-650`).
- A use of `AnyAwaitable` in run-time code needs a new rule and a new identifier, LAMA0298, because the existing check LAMA0233 covers only compile-time template-only symbols (ENG27 `Templating\TemplatingCodeValidator.Visitor.cs:149-205`).
- The event limitation. `DelegateEqualityRequired` also replaces the clause "the method reference is an event handler" of `MethodReferenceReceiverNotSupported`, so that every event site that needs a wrapper reports one limitation.
- `PullAction.None` at a site is reported with LAMA1012 and a clause, without a new member of `NonInterceptableReason`, because the provider already knows the value that it returned.
- The public `InterceptorParameterRole` and `AddCallerInfoParameter` are removed. `InterceptorArgument` gives the source of a parameter, and `AddParameter` with `CallerInfo` replaces `AddCallerInfoParameter`. An added parameter has no default, so the example of section [5.6.8](05b-api-providers-contexts-results.md#568-parameter-binding-and-the-signature-builder) declares `int callerLine` without `= 0`.
- The `IMethod` shorthands of the registration surfaces receive an optional `[Durable]` `bind` function, so that a shorthand can use an existing method whose parameter names differ from those of the target.
- An existing method can now drop an argument of the site, because the canonical binding matches names. E7 checks that every required parameter has a source, instead of a count.
- The await example is written `await Await_Interceptor( this.LoadAsync( id ), cancellationToken: ct )`, with a named argument, because added arguments are always named.

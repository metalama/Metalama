# Impact of .NET 11, C# 15 and Roslyn 5.10 on the design-time pipeline, Workspaces, LinqPad, the test frameworks and the analyzer shim

Analyst 5 of 8. Repository state: `/home/user/Metalama`, branch `topic/2027.0/26-09-03-update-eng-7e3j07`. All paths below are relative to that root unless they start with `/home/user/metalama.premium`. External sources were fetched on 2026-09-03 and are named where used. Nothing was built and no test was run.

## Summary

1. A `partial union` is not recognised as partial by the code model, so the design-time generator reports LAMA0048 instead of producing the partial file, and the LAMA0048 code fix then adds a second `partial` modifier (DT-1).
2. Once DT-1 is fixed, the generator emits `partial struct` for a union, which Roslyn rejects with CS0261 because the partial parts have different kinds (DT-2).
3. The generated design-time hashers were produced from a grammar with the C# 15 nodes stripped, so a rename of a union, a change of its modifiers, or a change of a labeled `break` target inside a template is invisible to the design-time diff until the grammar is refreshed from the stable Roslyn 5.10 (DT-3).
4. The consumed Roslyn build `5.10.0-1.26365.3` is dated 2026-07-15 and predates the commit that added `LanguageVersion.CSharp15` (2026-08-11); C# 15 is therefore not a language version in the current 5.10 variant, and `@LanguageVersion(15.0)` tests are silently skipped on both variants (DT-7).
5. Every shipped package that depends on `Microsoft.CodeAnalysis.*` at `5.10.0-1.26365.3` (Workspaces, AspectTesting, and the LinqPad driver metadata) cannot be restored from nuget.org, which serves nothing above 5.9.0 (DT-8).
6. `MSBuildInitializer` rejects a .NET SDK whose major version exceeds the host runtime major, so a .NET 10 host (the Workspaces package is `net10.0` only) fails on a machine that carries only the .NET 11 SDK (DT-9).
7. The analyzer shim serves any host at Roslyn 5.10 or above from the 5.10.0 variant, including 5.11 and 6.0, and this is pinned by tests; no change is needed (non-finding).
8. The RPC and cross-version contracts transport no type kind, syntax kind or language version; no change is needed (non-finding).

### DT-1: A `partial union` is reported as not partial, and the code fix duplicates the modifier

- Where: `Metalama.Framework/src/Metalama.Framework.Engine/CodeModel/Source/SourceNamedTypeImpl.cs:329-349` (`IsPartial`), `Metalama.Framework/src/Metalama.Framework.Engine/Utilities/Roslyn/SyntaxKindExtensions.cs:33-35` (`IsTypeDeclaration`), `Metalama.Framework/src/Metalama.Framework.Engine/Pipeline/DesignTime/DesignTimeSyntaxTreeGenerator.cs:158-171` and `:940-951`, `Metalama.Framework/src/Metalama.Framework.DesignTime/CodeFixes/TheCodeFixProvider.cs:57`, `:164-175`, `:187-192`.
- What happens today: `IsPartial` reads the modifiers only when the primary declaration satisfies `SyntaxKind.IsTypeDeclaration`, which lists class, struct, interface, record and record struct. `UnionDeclaration` (kind name from `eng/src/GenerateMetaSyntaxRewriter/Syntax-5.10.0.xml:1954-1978`, where `UnionDeclarationSyntax` derives from `TypeDeclarationSyntax`) is not in the list, so the `_ => default` arm returns an empty token list and `IsPartial` is `false` for `public partial union U(...)`. `ProcessTransformationsOnType` then reports `GeneralDiagnosticDescriptors.TypeNotPartial` (LAMA0048) at line 161 and returns without generating a file; `IsInNonPartialSourceType` gives the same answer for types nested in the union. `TheCodeFixProvider` registers LAMA0048 as fixable (line 57), finds the declaration through `BaseTypeDeclarationSyntax` (line 190, which does match a union) and appends a `partial` token (line 173), so applying the fix to a union that is already partial produces `public partial partial union U`, which is CS1004. The C# 15 proposal (`proposals/csharp-15.0/unions.md`, fetched 2026-09-03) permits `partial` on a union declaration and permits members in its body, so this scenario is a supported one: an aspect that introduces a member into a partial union.
- Consequence class: diagnostic reported (a wrong LAMA0048), and silent wrong output (no generated partial file, so introduced members are invisible in the editor).
- Proposed change: make `SyntaxKindExtensions.IsTypeDeclaration` and `IsBaseTypeDeclaration` (line 41) recognise the union kind. The 5.0.0 variant compiles the same source against Roslyn 5.0, which has no `SyntaxKind.UnionDeclaration`, and the repository forbids production branches on a variant constant (`Metalama.Framework/docs/testing.md:58`; FACTS: zero `#if ROSLYN_*` in production). Resolve the kind once at start-up with `Enum.TryParse<SyntaxKind>("UnionDeclaration", out var kind)` into a static field, in the manner of the numeric casts of `Metalama.Framework/src/Metalama.Framework.Engine/Utilities/AllLanguageVersions.cs:14-18`, rather than hard-coding the value 9082 recorded in FACTS, because a preview value may move before the stable release. Add a design-time aspect test (see the test plan under DT-7) and a unit test for `IsPartial` on a union.
- Size: M.
- Confidence: verified for the code path. That a union symbol reaches this code as an ordinary `INamedType` is verified on Roslyn main (`src/Compilers/CSharp/Portable/Symbols/EnumConversions.cs` maps `DeclarationKind.Union` to `TypeKind.Struct`, so `SourceNamedTypeImpl.cs:69-79` returns `TypeKind.Struct` and does not throw) and is plausible for the July build.
- Open questions: whether the stable Roslyn 5.10 keeps `UnionDeclarationSyntax` as a `TypeDeclarationSyntax` (the July grammar says so). Whether the code model should expose `INamedType.IsUnion`, which is a code-model theme; Roslyn main exposes `ITypeSymbol.IsUnion` (`src/Compilers/Core/Portable/Symbols/ITypeSymbol.cs`).

### DT-2: The generated partial part of a union is emitted as `partial struct`, which conflicts with the union declaration

- Where: `Metalama.Framework/src/Metalama.Framework.Engine/Pipeline/DesignTime/DesignTimeSyntaxTreeGenerator.cs:697-790` (`CreatePartialType`), `:817-823` (`AddHeader`), `:506-523` (`AddPartialModifierToTypes`); `Metalama.Framework/src/Metalama.Framework.Engine/CodeModel/Source/SourceNamedTypeImpl.cs:69-79` and `:173`.
- What happens today: `CreatePartialType` switches on `INamedType.TypeKind` and `IsRecord`. A union symbol has `TypeKind.Struct` (Roslyn `EnumConversions.cs`) and `IsRecord == false` (the proposal states that a union is a plain struct and that `record union` is not supported), so the `TypeKind.Struct when !type.IsRecord` arm at line 749 emits `partial struct U { ... }`. Roslyn reports `ERR_PartialTypeKindConflict` (CS0261) when two partial parts of one type have different declaration kinds (`src/Compilers/CSharp/Portable/Symbols/Source/SourceMemberContainerSymbol.cs` on main, `if (t.IsPartial && other.IsPartial) diagnostics.Add(ErrorCode.ERR_PartialTypeKindConflict, ...)`), so the generated file breaks the compilation in the editor as soon as DT-1 lets it be generated. `AddHeader` also matches concrete syntax types (class, struct, record, interface, namespace) and would not put the generated-code header on a `UnionDeclarationSyntax`. The `_ => throw new AssertionFailedException` arm at line 788 is not reached for unions, and if it were, the failure would be contained per group and reported as LAMA0049 (lines 86-105), not as a crash.
- Consequence class: diagnostic reported (CS0261 from the generated document), and the introduced members remain unusable at design time.
- Proposed change: detect a union in `CreatePartialType` (either from the primary declaration syntax kind resolved as in DT-1, or from a new `INamedType.IsUnion` fed by `ITypeSymbol.IsUnion`) and emit a `UnionDeclarationSyntax` part. `SyntaxFactory.UnionDeclaration` does not exist in Roslyn 5.0 and is marked experimental in the July 5.10 build, so build the part from text with `SyntaxFactory.ParseMemberDeclaration` using the parse options of the compilation (the generator already reuses them at lines 54-57), or route through the generated syntax factory of `eng/src/GenerateMetaSyntaxRewriter` once the stable grammar no longer strips the node. Extend `AddHeader` to `TypeDeclarationSyntax`. Add a `@TestScenario(DesignTime)` test whose expected `0.i.cs` shows the union part.
- Size: M.
- Confidence: verified for the generator; plausible for the exact Roslyn behaviour of a generated union part.
- Open questions: whether a partial union part may omit the case-type list. The proposal grammar makes `'(' case_types ')'` mandatory and says nothing about parts, whereas the grammar file declares `ParameterList` as optional on `UnionDeclarationSyntax` (`Syntax-5.10.0.xml:1965`). If every part must repeat the case types, the generator needs the case types, which the code model does not expose; Roslyn main exposes them on `ITypeSymbol` next to `IsUnion`.

### DT-3: The design-time diff hashers do not see C# 15 nodes until the grammar is refreshed from the stable Roslyn 5.10

- Where: `eng/src/GenerateMetaSyntaxRewriter/Model/TreeReader.cs:19` and `:35-43` (`RemoveExperimentalDeclarations`), `eng/src/GenerateMetaSyntaxRewriter/Generator.cs:615-712` (`GenerateHasher`), `eng/src/GenerateMetaSyntaxRewriter/GenerateMetaSyntaxRewriter.cs:46-47`, `Metalama.Framework/src/Metalama.Framework.DesignTime/Metalama.Framework.DesignTime.csproj:34-35`, `Metalama.Framework/src/Metalama.Framework.DesignTime/Pipeline/Diff/BaseCodeHasher.cs:19`, `Metalama.Framework/src/Metalama.Framework.Sdk/Utilities/Roslyn/SafeSyntaxWalker.cs:39`, `Metalama.Framework/src/Metalama.Framework.DesignTime/Pipeline/Diff/DiffStrategy.cs:73-93`, `Metalama.Framework/src/Metalama.Framework.DesignTime/Pipeline/Diff/PartialTypesVisitor.cs:38-42`, `Metalama.Framework/src/Metalama.Framework.DesignTime/Pipeline/Diff/PartialTypesHasher.cs:43-47`, `Metalama.Framework/src/Metalama.Framework.DesignTime/Pipeline/Diff/SyntaxTreeChange.cs:111`.
- What happens today: `RunTimeCodeHasher` and `CompileTimeCodeHasher` are generated with one `Visit<Node>` override per grammar node, and the generator strips every node and field that carries `ExperimentalUrl` (FACTS: `UnionDeclarationSyntax`, `WithElementSyntax`, `UnsafeExpressionSyntax`, and the `Name` field of `BreakStatementSyntax` and `ContinueStatementSyntax`). Two consequences follow. First, `UnionDeclarationSyntax` has no override, so `CSharpSyntaxWalker.DefaultVisit` runs; the walker is constructed with `SyntaxWalkerDepth.Node` (`SafeSyntaxWalker.cs:39`), which visits child nodes and skips tokens, so the union identifier, its modifiers and the `union` keyword contribute nothing to the hash, while the case types, base list and members still do. Second, the generated `VisitBreakStatement` and `VisitContinueStatement` hash only the keyword and the semicolon, because the `Name` field was removed before generation, so the label of a labeled `break` or `continue` is never hashed even by `CompileTimeCodeHasher`, which otherwise hashes bodies. `DiffStrategy.IsDifferent` treats an equal hash as no change (lines 80-85), so the pipeline is not re-run. Observable effects: renaming a union, or adding `partial` to it in response to LAMA0048, in a file with no other change does not trigger re-analysis, so the stale result and the stale LAMA0048 persist until an unrelated edit; changing the target label of `break` or `continue` inside a template does not rebuild the compile-time project, so the template keeps its previous behaviour at design time. Separately, `PartialTypesVisitor` and `PartialTypesHasher` override only class, struct and record, so a partial union is never listed in `SyntaxTreeVersion.PartialTypes` and the partial-type invalidation of `SyntaxTreeChange.cs:111` and `DiffStrategy.cs:97-150` does not cover unions, whereas `DependencyCollector.cs:63-64` does register unions because it tests `BaseTypeDeclarationSyntax`.
- Consequence class: silent wrong output.
- Proposed change: as part of the update to the stable Roslyn 5.10 (`Metalama.Framework/docs/updating-roslyn.md:10-12`), copy the stable `Syntax.xml` over `Syntax-5.10.0.xml` and regenerate; the union node and the break and continue `Name` field lose their `ExperimentalUrl` when the features ship in C# 15, so the generator will emit the missing overrides and hash the missing field. Add `VisitUnionDeclaration` overrides to `PartialTypesVisitor` and `PartialTypesHasher` under the same variant constraint as DT-1 (a walker override cannot be resolved by name, so these two classes need a `DefaultVisit` that tests the resolved kind, or the override must live in a file compiled for the 5.10 variant only, which is a policy exception to record). Add a `DiffStrategy` unit test that renames a union and changes a `break` label and asserts that the hash changes, skipped at run time when `LanguageVersionFacts.TryParse("15.0")` fails.
- Size: S for the regeneration, M with the tests and the partial-type visitors.
- Confidence: verified for the generator and the walker depth; the exact token behaviour of `CSharpSyntaxWalker.DefaultVisit` is standard Roslyn behaviour and was not executed here.
- Open questions: whether the stable Roslyn 5.10 grammar still marks any of these nodes experimental. If it does, the repository policy that experimental features are unsupported (`updating-roslyn.md:11`) leaves the gap open, and the DT-1 and DT-2 work would be pointless for that release.

- What happens today: `MSBuildInitializer` lists the SDKs with `dotnet --list-sdks` and keeps only those whose major version is at most `Environment.Version.Major`, then registers the highest one. The filter is correct, because the MSBuild assemblies of an SDK target the runtime of that SDK and cannot load into an older runtime. The Workspaces package is `net10.0` only (the comment at lines 5-8 explains why), and the LinqPad driver is `net10.0-windows`; the samples state that LINQPad 9 is required, and third-party queries found on GitHub describe LINQPad 9 as running on .NET 10 (`wcrowe/LINQPad-Queries`, header "LINQPad 9 / .NET 10"), which is the only evidence available here since nuget.org carries no `LINQPad.Runtime` 9.x package and linqpad.net is blocked. Under PB-2027.0 the .NET 11 SDK is in the supported set, and a developer who installs Visual Studio 2027 alone has the .NET 11 SDK and not necessarily the .NET 10 SDK. For such a machine, a .NET 10 host throws `MSBuildInitializationException` with the message at lines 91-94, which already names the cause. A .NET 11 host (a `net11.0` application referencing the `net10.0` asset) selects the .NET 11 SDK and loads its MSBuild against the `Microsoft.Build` 18.0.2 compile-time reference; that works as long as MSBuild keeps its frozen assembly version (`Directory.Packages.md:309`), and the pin must not rise because the .NET 10 SDK remains the lowest host (`Directory.Packages.props:35-52`).
- Consequence class: assertion or crash (an exception at workspace load), on a plausible but unverified environment.
- Proposed change: document in the Workspaces and LinqPad READMEs that the host runtime major decides which SDK is usable and that a .NET 10 host needs a .NET 10 SDK; consider a `net11.0` target for the LinqPad driver only if a LINQPad release hosts .NET 11, which is unknown. No code change is proposed for the filter.
- Size: S.
- Confidence: plausible (the code is verified; the LINQPad host runtime and the Visual Studio 2027 default SDK set are not).
- Open questions: the runtime of LINQPad 9 and of any later LINQPad; whether the Roslyn 5.10 build host process (`net10.0` and `net472` only, csproj lines 5-8) rolls forward to .NET 11 on a machine without a .NET 10 runtime (the comment in Roslyn's `src/Workspaces/MSBuild/Core/Microsoft.CodeAnalysis.Workspaces.MSBuild.csproj` on main says the deployed build host is used so that it can "rollforward to a runtime that supports the SDK version", which suggests that it does).

## Non-findings

- Analyzer shim and variant selection. `RoslynVariantPolicy.TryGetVariantName` (`Metalama.Framework/src/Metalama.Framework.CompilerExtensions/RoslynVariantPolicy.cs:30-54`) returns `5.10.0` for every host at 5.10 or above, so a Visual Studio 2027 update presenting Roslyn 5.11 or 6.0 is served by the latest variant; `RoslynVariantPolicyTests.cs:36-45` pins 5.10, 5.10.0, 5.11.0 and 6.0.0. `ResourceExtractor.GetHostRoslynVersion` (`ResourceExtractor.cs:633-656`) reads the assembly version of `Microsoft.CodeAnalysis` and handles the JetBrains build. `AssemblyResolutionPolicy.SelectAlreadyLoadedAssembly` (`AssemblyResolutionPolicy.cs:61-80`) accepts a same-or-higher version for non-embedded assemblies, so a host Roslyn above the compile-time reference binds. A host below 5.0 gets no variant and a report file (`ResourceExtractor.cs:157-211`), and the compiler entry point reports LAMA0087 (`MetalamaSourceTransformer.cs:23-31`, `:48-63`). Every other entry point routes through `TryCreateInstance` and holds no version literal (`MetalamaSourceGenerator.cs:25-59`, `MetalamaDiagnosticAnalyzer.cs:35-51`, `MetalamaDiagnosticSuppressor.cs:27-44`, `MetalamaGeneratedCodeAnalyzer.cs:28`, `AdditionalDiagnosticAnalyzer.cs:24`). The embedded resource lists (`Metalama.Framework.CompilerExtensions.csproj:53-70`) name the `net472` and `net10.0` outputs of `Metalama.Framework.CompilerExtensions.Resources.csproj:6`, and `platform-support.md:141-160` records that the Visual Studio private runtime is .NET 10 on the Roslyn 5.10 branch, so no flavour changes. The residual risk is binary: the 5.10.0 variant is compiled against the July preview and loads into the stable Roslyn 5.10 of Visual Studio 2027 with no version check other than the major and minor; an API that changed between the two would surface as a load or missing-method exception written to the crash-report directory (`ResourceExtractor.cs:259-307`) and as nothing in the editor. DT-8 closes this by consuming the stable build before release.
- RPC and cross-version contracts. The only kind on the wire is `AspectExplorerDeclarationKind` with the values `Default` and `ReturnParameter` (`Metalama.Framework/src/Metalama.Framework.DesignTime.Contracts/AspectExplorer/AspectExplorerAspectInstance.cs:60-66`). No file under `DesignTime.Rpc`, `DesignTime.Contracts` or `DesignTime/VisualStudio` mentions `TypeKind`, `SyntaxKind` or `LanguageVersion` (grep). `ProjectKey` carries the assembly name, a preprocessor-symbol hash and a Metalama flag (`ProjectKey.cs:21-25`). Declarations cross the pipe as `SerializableDeclarationId` strings resolved through `SerializableDeclarationIdProvider.ToSymbol.cs:21-39`, and a union is an ordinary named type symbol to that resolution. `RpcContractMessagePackOptions` (`RpcContractMessagePackOptions.cs:37-78`) constrains typeless deserialization to `[RpcContract]` types and `SymbolKey`; nothing there depends on the language version.
- Preview and code-action transport. `SerializableSyntaxTree` carries text and annotations; `ToSyntaxTree` re-parses with the caller's options (`Metalama.Framework/src/Metalama.Framework.Engine/DesignTime/JsonSerializationHelper.cs:41-49`, used by `PreviewTestRunner.cs:83` with the original tree options), and `ToSyntaxNode` uses `CSharpParseOptions.Default` (line 52) when a code action is applied in the user process (`CodeActionResult.cs:75`). With a stable Roslyn 5.10 whose `Default` is C# 15, C# 15 text parses; under the 5.0 variant a project cannot be at C# 15 in the first place. The omission of the project's preprocessor symbols in that call is pre-existing and unrelated to this release.
- Code lens and refactorings. `CodeLensServiceImpl` reasons on symbols and prints `symbol.Kind` (`CodeLensServiceImpl.cs:189`); `TheCodeRefactoringProvider` resolves `GetDeclaredSymbol(node)` for whatever node is under the caret (`TheCodeRefactoringProvider.cs:104-132`); neither switches on a declaration kind. The live template test runner locates its target by attribute (`LiveTemplateTestRunner.cs:51-56`).
- Design-time diff for `with(...)` elements. `WithElementSyntax` is stripped from the grammar, so it has no hasher override, but `DefaultVisit` still visits its `ArgumentList` child, whose arguments are hashed; only the `with` keyword token is lost, which cannot change without the argument list changing shape.
- Dependency collection. `DependencyCollector.AddDependency` tests `BaseTypeDeclarationSyntax` and the `partial` token (`DependencyCollector.cs:63-64`), so partial unions register partial-type dependencies.
- Generated syntax trees at design time. The generator reuses the compilation's parse options (`DesignTimeSyntaxTreeGenerator.cs:54-57`), so generated documents share the project language version and preprocessor symbols, and `DesignTimeTestRunner` adds them to the input compilation unchanged (`DesignTimeTestRunner.cs:58-66`).
- Workspaces packaging under PB-2027.0. The single `net10.0` target (`Metalama.Framework.Workspaces.csproj:18`) is what the baseline requires; a `net11.0` consumer resolves the `net10.0` asset. The `_WorkspacesMSBuildAssetTargetFramework` fallback to `net9.0` (lines 96-98) is dead once the package ships a `net10.0` folder, and the `Error` at lines 117-118 guards the packing. The `build/Metalama.Framework.Workspaces.targets` file imports `../buildTransitive/Metalama.Framework.Workspace.targets`, a path that does not exist (the real file is `Workspaces.targets`, plural); this has been so since the first public commit 046f2e18. It has no effect, because NuGet drops from the `build` asset list every file whose name also appears under `buildTransitive` (`LockFileUtils.AddMSBuildAssets` in NuGet.Client, fetched 2026-09-03), so only the `buildTransitive` file is ever imported. The file can be deleted or corrected at leisure.
- Workspaces MSBuild versions. `MicrosoftBuildVersion` is `18.0.2` with the rationale at `Directory.Packages.props:35-52`; the lowest host stays the .NET 10 SDK under PB-2027.0 (`Directory.Packages.md:18-20`), so the pin is unchanged by .NET 11. `Microsoft.Build.Locator` 1.7.8 and `Microsoft.VisualStudio.SolutionPersistence` 1.0.52 (`Directory.Packages.props:151-152`) have no dependency on the SDK major.
- LinqPad literals. The only framework literal is the `net10.0-windows` target (`Metalama.LinqPad.csproj:6`); `TargetFramework` strings elsewhere in the driver are project properties read at run time (`Permalink.cs:49`, `SchemaFactory.cs:52-55`). The driver compiles its typed data context with LINQPad's own Roslyn (`MetalamaScratchpadDriver.cs:167-180`), which is independent of the Metalama language version. `LINQPad.Reference` 1.4.0-preview.1 ships `netcoreapp3.0` and `net46` assets (nuspec on nuget.org), so it constrains nothing. The eng build packs `Metalama.LinqPad` alongside Workspaces (`eng/src/Program.cs:108`, `:123`, `:132`).
- Observation outside the .NET 11 scope: `Workspace.LoadProjectSetCoreAsync` accepts `.csproj`, `.sln` and `.slnf` only (`Workspace.cs:311-340`), and no file under Workspaces or LinqPad mentions `.slnx`, although `Microsoft.VisualStudio.SolutionPersistence` is referenced. Visual Studio 2026 and 2027 create `.slnx` solutions, so this is worth a separate issue.
- Test directives. `RequiredConstant` and `ForbiddenConstant` are evaluated against the `DefineConstants` metadata of the test assembly (`TestInput.cs:74-95`, `Metalama.Testing.AspectTesting.targets:58-61`); `@LanguageFeature` maps to `CSharpParseOptions.WithFeatures` (`TestOptions.cs:720-737`, `BaseTestRunner.cs:226-229`); `@DependencyLanguageVersion` shapes the dependency project (`BaseTestRunner.cs:421-424`). All three behave as documented in `Metalama.Framework/docs/testing.md:147-154`.
- Cross-version contracts and the `Metalama.Framework.DesignTime.Contracts.v2` assembly need no change for this release; nothing in the union, closed-class, labeled-break, collection-expression-argument, extension-indexer or static-interface-member features crosses a Metalama version boundary.

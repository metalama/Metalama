# 01. The C# 15 language version, the .NET 11 SDK as build host, and the stable Roslyn 5.10

Analysis of `/home/user/Metalama` (branch `topic/2027.0/26-09-03-update-eng-7e3j07`) on 2026-09-03. No file was modified, no build was run, no test was run. Line numbers refer to the working tree at that commit. Metalama.Compiler is not cloned; every dependency on it is listed in the last section as an assumption and is referenced from the findings as A1, A2, and so on.

## Summary

1. Every language version site stops at C# 14, and the two that matter most fail in opposite ways: the MSBuild clamp in `Metalama.Framework.targets:118-120` rewrites the SDK-implied `15.0` of a `net11.0` project to `12.0` with a misleading warning (LV-1), and an explicit `15.0` makes `VerifyLanguageVersion` throw in `ToDisplayStringSafe` so that the user sees `LAMA0001` with a crash report instead of `LAMA0052` (LV-2).
2. Adding C# 15 is a coordinated edit of `SupportedCSharpVersions`, `AllLanguageVersions`, `LanguageVersionExtensions` and `LanguageVersionProvider` (LV-3), with one design constraint: `SupportedCSharpVersions.Latest` is a constant shared by the Roslyn 5.0 and 5.10 variants, and C# 15 is valid only in the 5.10 variant, so `Latest` has to become variant-aware while `All` may stay shared.
3. The compile-time compilation is capped by the SDK major in `LanguageVersionProvider.cs:54-60`; the .NET 11 SDK maps to C# 14 today, so compile-time code cannot use C# 15 even when the run-time compilation does (LV-3, case d).
4. The build host pins the .NET SDK to 10.0.400 (`eng/src/Program.cs:26`) and nothing in the repository builds or tests under the .NET 11 SDK or against `net11.0`; the platform test excludes `net11.0` explicitly (LV-9). Nothing contradicts the statement that the `net10.0` toolset rolls forward, but nothing exercises it either.
5. The consumed `5.10.0-1.26365.3` is a build of Roslyn `main` that will never have a stable counterpart, and the November 2026 hosts carry Roslyn 5.12, so the stable transition is a renumbering of the latest variant from 5.10.0 to 5.12.0 (LV-12): about eight edit sites, listed in LV-13, and two silent failure modes, because extension assemblies declared for `TargetRoslynVersion=5.10.0` stop matching without any diagnostic and compile-time manifests that carry `V5_10_0` stop deserializing unless `5.10.0` is kept as a legacy version of the generator. A host presenting Roslyn 5.12 is served by the `5.10.0` variant correctly today.
6. `updating-roslyn.md` names two members that no longer exist (`ResourceExtractor.GetRoslynVersion`, `JsonSerializationBinder`) and one edit that the latest-variant case does not need (LV-14).

### LV-1. The `LangVersion` clamp rewrites the SDK-implied 15.0 to 12.0 and warns with the wrong explanation

- Where: `Metalama.Framework/src/Metalama.Framework.Package/build/Metalama.Framework.targets:115-121` (the rewrite), `:243-247` (the warning), imported for user projects through `buildTransitive/Metalama.Framework.targets:2`.
- What happens today: the condition at line 118 accepts only `12.0`, `13.0`, `14.0`, `default`, `latest`, `latestMajor` and `preview`. A `net11.0` project whose `LangVersion` the SDK sets to `15.0` (A1) and that Metalama.Compiler marks as implicitly set (A1) is rewritten to `12.0` at line 120. The warning at line 245 then states that the version was updated "because 12.0 is the lowest version supported by Metalama Framework", which is false in this direction. The comment at line 115-117 shows that the rewrite was written for target frameworks whose implied version is below C# 12, and the whitelist enumerates the versions known at the time instead of comparing. The same evaluation happens in the design-time build, so the IDE sees C# 12 as well.
- Consequence class: build or restore error when user code or aspect code uses any feature of C# 13, 14 or 15 (the compiler reports the "feature is not available in C# 12.0" family of errors). Diagnostic reported, with a misleading text and no warning code, when the code happens to fit C# 12. The `Warning` task at line 244 has no `Code` attribute, so `NoWarn` cannot address it.
- Proposed change: replace the enumeration by a comparison. Keep the rewrite only when the implied value is numeric and lower than `12.0`, for example a condition on `$([MSBuild]::VersionLessThan('$(LangVersion)', '12.0'))` guarded by a numeric test, and leave every named value and every version at or above `12.0` untouched. Give the warning a code (the `LAMA06xx` range is used by the platform checks at lines 329-369). Rewrite the text so that it says what happened. Add a standalone scenario `Standalone/DefaultLanguageVersion/DotNet11` that targets `net11.0`, leaves `LangVersion` empty, and uses a C# 14 feature, mirroring `DefaultLanguageVersion/DotNet/DotNet.csproj:5-11` and `Test.cs:24-27`, which target `net10.0` and use a C# 12 feature and therefore cannot detect this defect. That scenario needs the `net11.0` targeting pack on the agents (see LV-9).
- Size: S for the targets, M including the container change of LV-9.
- Confidence: verified for the targets logic; plausible for the value `15.0` and for `LangVersionImplicitlySet` (A1).
- Open questions: whether Metalama.Compiler computes the implied version from its own target-framework table (the comment at line 115 says "according to the current target framework") or copies the SDK value; if it has its own table, `net11.0` may not be marked at all and the rewrite would not fire, which would leave a C# 15 compilation to reach LV-2 instead.

### LV-2. `VerifyLanguageVersion` throws instead of reporting `LAMA0052` for C# 15

- Where: `Metalama.Framework/src/Metalama.Framework.Engine/Pipeline/CompileTime/CompileTimeAspectPipeline.cs:67` (effective version), `:82-89` (the report), `Metalama.Framework/src/Metalama.Framework.Engine/Utilities/Roslyn/LanguageVersionExtensions.cs:33-39` (no case for `1500`, throws `ArgumentOutOfRangeException`); the exception path is `Metalama.Framework/src/Metalama.Framework.Engine/Pipeline/SourceTransformer.cs:145-158`, `Metalama.Framework/src/Metalama.Framework.Engine/Pipeline/CompileTime/CompileTimeExceptionHandler.cs:186`, `Metalama.Framework/src/Metalama.Framework.Engine/Diagnostics/GeneralDiagnosticDescriptors.cs:25-32` (`LAMA0001`, error).
- What happens today: with an explicit `15.0` (case b), or with `default`, `latest` or `latestMajor` once the compiler maps them to C# 15 (A3), the first syntax tree carries language version `1500`. It is not in `SupportedCSharpVersions.All`, so line 87 evaluates `languageVersion.ToDisplayStringSafe()` to build the `LAMA0052` arguments, and that call throws. `SourceTransformer` catches the exception, `CompileTimeExceptionHandler` writes a crash report and reports `LAMA0001` ("Unexpected exception occurred in Metalama"), and `isHandled` is true, so the build fails with an error that asks the user to open a support ticket. The same helper is used by `RoslynVersionSyntaxVerifier.cs:37` and `TemplateExpansionContext.cs:874-875`, which cannot receive `1500` today but will as soon as LV-3 is applied.
- Consequence class: assertion or crash, surfaced as a `LAMA0001` error. The build does fail, so no wrong output is produced, but the designed diagnostic is not the one the user sees.
- Proposed change: add `(LanguageVersion) 1500 => "15.0"` to `ToDisplayStringSafe`, and replace the throwing default arm by a formatted fallback such as `$"{(int) version / 100}.{(int) version % 100}"` for any value of at least `700`, so that a future version can never turn a diagnostic into a crash again. Add a unit test for values `1300`, `1400`, `1500` and `1600` in `Metalama.Framework.Tests.UnitTests`.
- Size: S.
- Confidence: verified. The prerelease Roslyn 5.10 must accept `15.0` in `LanguageVersionFacts.TryParse` for the value to reach this site (A3); on the stable 5.10 it will.
- Open questions: none.

## Assumptions about Metalama.Compiler

- A1. `LangVersionImplicitlySet`. `Metalama.Framework.targets:115-118` expects Metalama.Compiler to set `LangVersionImplicitlySet=True` when the project does not define `LangVersion`, with `LangVersion` holding the SDK's implied value at the time the rewrite is evaluated. The analysis assumes the .NET 11 SDK implies `15.0` for `net11.0`, following the `net8.0` to `12.0`, `net9.0` to `13.0`, `net10.0` to `14.0` sequence that the current list at line 118 encodes. If Metalama.Compiler derives the value from its own target-framework table, `net11.0` may be unmarked, and LV-1 does not fire while LV-2 does.
- A2. Roslyn version, the prerequisite of the renumbering. `MetalamaCompilerVersion` is `2027.0.0` (`eng/AutoUpdatedVersions.props:3`) and Metalama.Compiler builds on the Roslyn named by `RoslynApiMaxVersion` (`Directory.Packages.props:25-28`, `docs/updating-roslyn.md:9-10`, whose first step is "Update Metalama.Compiler first"). The renumbering of LV-12 and LV-13 requires Metalama.Compiler to build on a Roslyn 5.12 build before this repository binds its latest variant against 5.12: a payload bound against `5.12.0.0` does not load in a compiler that hosts `5.10.0.0`, and `RoslynVariantPolicy` would then serve that compiler the `5.0.0` variant, which limits every build to C# 14 without any diagnostic. The analysis assumes that the 2027.0 compiler moves to a 5.12 prerelease first and to the stable 5.12 in November 2026, and that any Roslyn at or above 5.10 supports C# 15 (`FACTS.md`, C# 15 feature list). The compile-time compilation is compiled by the host's Roslyn, so the compiler's Roslyn is what `SupportedCSharpVersions.ToLanguageVersion` for `RoslynApiVersion.Current` must describe.
- A3. Command-line language version. The analysis assumes that the compiler's `LanguageVersionFacts.TryParse` accepts `15.0` and that `MapSpecifiedToEffectiveVersion` maps `default`, `latest` and `latestMajor` to C# 15, as the `main` branch of Roslyn does per `FACTS.md`. Whether the consumed July 2026 prerelease already does so is not known; the stable will.
- A4. Host runtime and toolset. `platform-support.md:338-339` records that the `net10.0` toolset and the `Metalama.Compiler.Sdk` tasks declare `rollForward=Major` and run on .NET 11, and `:345-349` records two places that drift when the SDK floor moves. Nothing in this repository contradicts either statement, and nothing tests them (LV-9).
- A5. Properties consumed from the compiler. `Metalama.CompilerVisibleProperties.props:56` states that more properties are exported by Metalama.Compiler; the engine reads the names in `MSBuildPropertyNames.cs:64-102`, of which `MSBuildProjectFullPath`, `TargetFramework`, `NuGetTargetMoniker`, `Configuration`, `MetalamaDebugTransformedCode` and `MetalamaCompilerTransformedFilesOutputPath` are not in the props file of this repository and are therefore assumed to come from the compiler. A rename on the compiler side would be silent, because `MSBuildProjectOptions` returns null or the default for a missing option.
- A6. API surface. The engine implements the compiler's `ISourceTransformer` contract through `Metalama.SourceTransformer/SourceTransformer.cs` and `Metalama.Framework.Engine/Pipeline/SourceTransformer.cs:100-170` (`TransformerContext.ReportDiagnostic`, `AddResources`, `AddSyntaxTreeTransformations`, `Compilation`, `Resources`, `ProjectOptions`), registers an `IExceptionReporter` from `Metalama.Compiler.Services` (`SourceTransformer.CompilerServiceProvider.cs:54-57`), and embeds `Metalama.Compiler.Interface.dll` from the `Metalama.Compiler.Sdk` package (`Metalama.Framework.Engine.csproj:29-33`). `UseMetalamaCompiler=Private` (`Metalama.Framework.Engine.csproj:11`, `Metalama.Framework.Tests.UnitTests.csproj:11`) and `MetalamaCompilerDisablePackCustomization` (`Metalama.Framework.Engine.csproj:10`) are compiler-side properties assumed to keep their names.
- A7. `LAMA0622`. The host-runtime check `MetalamaCompilerCheckHostRuntime` named at `platform-support.md:340-342` lives in the compiler's targets and is assumed to exist as described; this repository's own check (`MetalamaCheckSupportedToolchain`) covers the SDK version and MSBuild version only.

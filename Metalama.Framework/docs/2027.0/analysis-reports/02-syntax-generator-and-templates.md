# 02. Syntax generator, template compiler, template language version, analyzers

All paths are relative to `/home/user/Metalama` unless stated otherwise. Roslyn API shapes (for example the presence of a four-argument `SyntaxFactory.BreakStatement` overload, or whether the binder or the parser checks a feature's language version) could not be verified because neither Metalama.Compiler nor a Roslyn 5.10 package is present on this machine; such statements are marked as assumptions.

## Summary

1. The generator strips every node and field with `ExperimentalUrl` (`TreeReader.cs:90-129`), so today the generated code of the 5.10.0 variant knows nothing of `UnionDeclarationSyntax`, `WithElementSyntax`, `UnsafeExpressionSyntax` or `BreakStatementSyntax.Name`. Regeneration is automatic: `Build.ps1 prepare` (and therefore the CI `test` run) calls `GenerateMetaSyntaxRewriter.Generate` and the outputs are git-ignored, so the change propagates the moment `Syntax-5.10.0.xml` is replaced by the stable grammar and `RoslynApiMaxVersion` points to a package that no longer marks those members `[Experimental]`.
2. Regeneration alone is not enough: `SupportedCSharpVersions.ToLanguageVersion(V5_10_0)` returns C# 14, so the regenerated `RoslynVersionSyntaxVerifier` would accept C# 15 syntax in a C# 14 template and would record `UsedApiVersion = V5_10_0` without ever reporting LAMA0232 or LAMA0282. It must return C# 15 in the same change.
3. Until regeneration, C# 15 syntax in a run-time template body either drops information silently (`break outer;` becomes `break;`) or crashes with an `InvalidCastException` wrapped in `SyntaxProcessingException` (`with(...)` element). Neither path produces a diagnostic. Both are reachable only once C# 15 is added to `SupportedCSharpVersions.All`, because today LAMA0052 or the compiler's own parse error stops the template compiler first.
4. Labeled `break` and `continue` are unsupported by design of the annotator: `VisitBreakStatement` uses the scope of the innermost loop and ignores the label, and `LabeledStatementSyntax` has no scope handling. Modelling labels is the one piece of real template-compiler work that C# 15 requires.
5. `unsafe(...)` remains experimental; the annotator reports LAMA0101 for the `unsafe` statement but has no override for the expression, so the expression passes through the annotator and reaches the compile-time compilation. A generic guard for experimental node kinds is proposed.
6. Nested `union` declarations and extension blocks inside compile-time classes fall into the `default:` branch of `ProduceCompileTimeCodeRewriter.VisitTypeDeclaration` and are copied verbatim without classification, manifest entry or template compilation; extension indexers only widen a gap that exists for C# 14 extension blocks already.
7. Raising the template language to C# 15 touches six constants and requires a per-variant branch of `SupportedCSharpVersions.Latest` and `All` (the Roslyn 5.0 variant cannot parse C# 15), which the current doctrine forbids and which the 2026.x code did with `#if ROSLYN_5_0_0_OR_GREATER`. The repository-wide `MetalamaTemplateLanguageVersion` must stay at 14.0 while `RoslynApiMinVersion` is 5.0.0.
8. Neither analyzer project that runs on user code switches over `SyntaxKind` with a throwing default; they are operation-based, and their throwing defaults are over `IOperation` types that the registration filters already exclude.

### TP-3. Labeled `break` and `continue` are not modelled by the annotator; the label is dropped silently by the generated rewriter

- Where: `Metalama.Framework/src/Metalama.Framework.Engine/Templating/TemplateAnnotator.cs:1375-1379`, `:1414-1424`, `:1360-1361`, `:2500-2506`, `:2533-2537`, `:2559-2563`, `:2927-2933`, `:627-643`, `:676-680`; `Metalama.Framework/src/Metalama.Framework.Engine/Templating/TemplateAnnotator.ScopeContext.cs:21` and `:123-132`; `Metalama.Framework/src/Metalama.Framework.Engine/Templating/TemplateCompilerRewriter.cs:196-266`, `:625-630`, `:2266-2338`, `:2908-2980`; `Metalama.Framework/src/Metalama.Framework.Engine/Templating/MetaSyntaxRewriter.cs:106-139`; `Metalama.Framework/src/Metalama.Framework.Sdk/Utilities/Roslyn/SafeSyntaxRewriter.cs:44-62`; `eng/src/GenerateMetaSyntaxRewriter/Generator.cs:481-519`.
- What happens today, template scope classification: `VisitBreakStatement` and `VisitContinueStatement` annotate the statement with `CurrentBreakOrContinueScope` (`TemplateAnnotator.cs:1375-1379`), which every loop and switch sets to its own scope for its body (`ScopeContext.cs:123-132`, callers at `:1414`, `:2500`, `:2533`, `:2559`, `:2927`). The `Name` child is never read, so a `break outer;` inside a run-time inner loop nested in a compile-time outer loop is classified run-time, and the reverse is classified compile-time, whatever the label designates. Neither `TemplateAnnotator` nor `TemplateCompilerRewriter` overrides `VisitLabeledStatement` (override lists at `TemplateAnnotator.cs:702-3505` and `TemplateCompilerRewriter.cs:306-3289`); a labeled statement gets no scope annotation of its own because `AddScopeAnnotationToVisitedNode` returns statements untouched (`TemplateAnnotator.cs:676-680`), and its transformation kind is then decided by `IsCompileTimeCode` from the parent chain or from an annotation forced by an enclosing compile-time `if` or `foreach` (`TemplateAnnotator.cs:1360-1361`, `:1423`; `TemplateCompilerRewriter.cs:196-266`).
- What happens today, run-time scope: the generated `TransformBreakStatement` builds `SyntaxFactory.BreakStatement(attributeLists, breakKeyword, semicolonToken)` from the stripped field list (`Generator.cs:481-519`), so the label is dropped and the generated run-time code contains a plain `break;` that exits the innermost loop of the target. No diagnostic.
- What happens today, compile-time scope: the statement is kept as compile-time C# (`TemplateCompilerRewriter.cs:2266-2287`, `case StatementSyntax`). The base `CSharpSyntaxRewriter.VisitBreakStatement` visits `Name` through `VisitIdentifierName` (`TemplateCompilerRewriter.cs:2908-2980`), where the compile-time branch delegates to `_compileTimeOnlyRewriter` (`:2980`), so the label identifier is preserved. The result is a compile-time `break outer;` inside the compiled template; whether the compile-time compilation accepts it depends on TP-8 (compile-time language version) and on whether Roslyn enforces `IDS_FeatureLabeledBreakContinue` in the binder or only in the parser, since `CSharpSyntaxTree.Create` does not re-parse (`CompileTimeCompilationBuilder.cs:349-354`).
- What happens today, a labeled statement whose loop is run-time inside a compile-time block: the forced `CompileTimeOnly` annotation (`TemplateAnnotator.cs:1423`) makes the generated `VisitLabeledStatement` take the `base.VisitLabeledStatement` branch (`Generator.cs:419-420`), which casts the transformed child, an `InvocationExpressionSyntax`, to `StatementSyntax`. The `InvalidCastException` is wrapped into `SyntaxProcessingException` by `SafeSyntaxRewriter.Visit` (`SafeSyntaxRewriter.cs:56-61`). A labeled statement directly in the template body has no annotation and is transformed as run-time code (`TemplateCompilerRewriter.cs:239-262`, the `null` parent case returns `false`), which wraps a compile-time loop into a run-time labeled block through `TransformStatement` (`TemplateCompilerRewriter.cs:625-630`). Labels are useless in templates today because `goto` is rejected (`TemplateAnnotator.cs:2601-2606`), so none of these paths is covered by a test (`Tests/UnsupportedSyntax/GotoNotSupported.cs` is the only labeled statement in the template test suites).
- Reachability: a template containing `break outer;` is rejected before any of this runs while the aspect project is compiled at C# 14 or lower, because the parser reports the feature error and `TemplateCompiler.TryCompile` stops on source errors (`TemplateCompiler.cs:159-217`); C# 15 and `preview` are refused by `VerifyLanguageVersion` (`CompileTimeAspectPipeline.cs:62-90`) unless `MetalamaAllowPreviewLanguageFeatures` is set. Adding C# 15 to `SupportedCSharpVersions.All` (TP-8) opens all the paths above.
- Consequence class: silent wrong output (run-time scope, before regeneration); assertion or crash (labeled run-time loop inside a compile-time block); after regeneration, a run-time `break outer;` whose label was on a compile-time loop produces CS0159 in the transformed user code, which is a diagnostic reported in generated code.
- Proposed change: (1) in `TemplateAnnotator`, add `VisitLabeledStatement` that visits the inner statement and copies its scope annotation to the labeled statement, and record `label name -> scope` in `ScopeContext`; (2) in `VisitBreakStatement`/`VisitContinueStatement`, when `Name` is not null resolve the label scope from the context, annotate the statement with that scope, and report a new error (in the family of `TemplatingDiagnosticDescriptors`, next to LAMA0101) when a run-time `break` targets a compile-time loop, since the unrolled loop has no run-time counterpart; a compile-time `break` targeting a run-time loop must be annotated run-time so that the label survives in the generated code; (3) in `TemplateCompilerRewriter`, handle a labeled statement whose inner statement is run-time by transforming the whole labeled statement (the generated `TransformLabeledStatement` already exists) instead of letting the base rewriter cast. Because `BreakStatementSyntax.Name` is absent from Roslyn 5.0 and experimental in the current 5.10 package, step (2) must read the label through `node.ChildNodes().OfType<IdentifierNameSyntax>()` until the stable package is consumed, or be written after the package update. Add template tests under `Tests/Syntax/` for the four combinations (compile-time or run-time outer loop, compile-time or run-time inner loop) with `@LanguageVersion(15.0)` so that the Roslyn 5.0 variant skips them (`TestOptions.cs:681-699`).
- Size: M.
- Confidence: verified (annotation and generated factory paths), plausible (exact exception for the labeled run-time loop; the exact Roslyn base-visitor cast could not be read).
- Open questions: whether Roslyn checks `IDS_FeatureLabeledBreakContinue` in the parser only; if so, the compile-time compilation created with C# 14 parse options accepts a compile-time `break outer;` silently, and only the host Roslyn version decides.

### TP-5. `unsafe(...)` expressions are not rejected by the annotator

### TP-8. Raising the template language to C# 15

- Where: `Metalama.Framework/src/Metalama.Framework.Engine/Utilities/SupportedCSharpVersions.cs:31-43`, `:52-62`, `:149-159`; `Metalama.Framework/src/Metalama.Framework.Engine/Utilities/AllLanguageVersions.cs:14-18`; `Metalama.Framework/src/Metalama.Framework.Engine/Utilities/LanguageVersionProvider.cs:54-71`; `Metalama.Framework/src/Metalama.Framework.Engine/Utilities/Roslyn/LanguageVersionExtensions.cs:33-39`; `Metalama.Framework/src/Metalama.Framework.Engine/Templating/TemplateCompiler.cs:51`, `:58-79`; `Metalama.Framework/src/Metalama.Framework.Engine/Options/MSBuildProjectOptions.cs:167-181`; `Metalama.Framework/src/Metalama.Framework.Package/build/Metalama.Framework.targets:115-121`; `Directory.Build.props:11-16`; `Directory.Packages.props:23`; `Metalama.Framework/docs/testing.md:58`; `eng/RoslynVersions/Roslyn.5.10.0.props` (comment on `DefineConstants`); git commit `08d065a9` (diff of `SupportedCSharpVersions.cs`, which removed `#if ROSLYN_5_0_0_OR_GREATER` around `Latest` and `All`).
- Where the decision is made: `TemplateCompiler.TemplateLanguageVersion` is `ILanguageVersionProvider.GetCompileTimeLanguageVersion()` (`TemplateCompiler.cs:51`), overridden by `MetalamaTemplateLanguageVersion` when set and contained in `SupportedCSharpVersions.All` (`:58-79`). `LanguageVersionProvider` returns the minimum of the SDK-derived version (`>= 10 => CSharp14`, `:54-60`) and the project's `LangVersion` (`:62-71`); on the `msbuild.exe` path it uses `GetMaxLanguageVersion` of the bundled Roslyn (`:111`). The same value is the `MaximalAcceptableLanguageVersion` of the verifier and the parse-option version of the compile-time compilation (`CompileTimeCompilationBuilder.cs:349-354`, `:425-433`).
- How the constant is tested: `Standalone/TemplateLanguageVersion14` (README, and `Test.cs` using `field`), which asserts that a template may be written in C# 14 and states that the value is bounded by `RoslynApiMinVersion`; `CompileTimeCompilationBuilderTests.TemplateLanguageVersion` (`:1914-1967`) which checks the manifest's `LanguageVersion`; the aspect tests `Tests/Aspects/LanguageVersion/*_OldVersion.cs` which pin LAMA0282 with `@LanguageVersion(10)`; `Tests/Aspects/LanguageVersion/LanguageVersionPreview.cs` and `Tests/Aspects/Misc/LanguageVersion.cs` which pin the LAMA0051 and LAMA0052 message texts including the list of supported versions (`.t.cs` files); and `TestLanguageVersionProvider` which returns `SupportedCSharpVersions.Latest` for unit tests (`Metalama.Testing.UnitTesting/TestLanguageVersionProvider.cs:12`).
- What must change to accept C# 15 while a .NET 10 SDK host still compiles the compile-time compilation: (1) `Latest => CSharp15` and `All` including `CSharp15`, through `AllLanguageVersions.CSharp15` because Roslyn 5.0 has no `LanguageVersion.CSharp15` member; (2) `LanguageVersionProvider`: `>= 11 => CSharp15`, `>= 10 => CSharp14` (the cap on a .NET 10 SDK host is then C# 14, which is what keeps that host working); (3) `ToLanguageVersion` and `GetMaxLanguageVersion` as in TP-2; (4) `ToDisplayStringSafe`: `(LanguageVersion) 1500 => "15.0"`, otherwise LAMA0051 and LAMA0052 throw `ArgumentOutOfRangeException` while formatting the supported list (`LanguageVersionExtensions.cs:39`, `SupportedCSharpVersions.cs:45`); (5) `Metalama.Framework.targets:118`: add `'15.0'` to the accepted implicit `LangVersion` values, otherwise a `net11.0` project is rewritten to C# 12 with the `MetalamaCheckLangVersion` warning (FACTS, line 22); (6) update the `.t.cs` expectations that list the supported versions.
- The variant problem: the 5.0.0 variant is compiled from the same source against Roslyn 5.0, whose parser does not know C# 15; `SupportedCSharpVersions.DefaultParseOptions` is `Latest` (`:50`) and every aspect test parses with it (`BaseTestRunner.cs:216`), and `MSBuildProjectOptions.LanguageVersion` falls back to `Latest` when the host cannot parse the project's `LangVersion` (`:167-181`). A `Latest` of 1500 on Roslyn 5.0 would therefore make the 5.0.0 variant use an unknown version everywhere. The 2026.x code solved the same situation with `#if ROSLYN_5_0_0_OR_GREATER` around `Latest` and `All` (commit `08d065a9`), which the current doctrine forbids (`testing.md:58`, comment in `Roslyn.5.10.0.props`). Either the doctrine gets a documented exception for `SupportedCSharpVersions.Latest` and `All`, or `Latest` is derived at run time from `RoslynApiVersion.Current.ToLanguageVersion()`, which is a constant per variant without a preprocessor branch; the second form is recommended.
- The design-time floor: `Directory.Build.props:11-16` explains that the repository's own templates are bounded by `RoslynApiMinVersion` (5.0.0), so `MetalamaTemplateLanguageVersion` stays `14.0` for Metalama's own aspects. For user projects, mapping SDK 11 to C# 15 makes the default template language C# 15, and the compile-time assembly of such a project cannot be built inside Rider 2026.2 (Roslyn 5.0 host, PB-2027.0). This is a product decision: either keep the SDK 11 default at C# 14 and require `MetalamaTemplateLanguageVersion=15.0` as an opt-in until `RoslynApiMinVersion` is 5.10, or accept the Rider limitation.
- Tests to copy for C# 15: `Tests/Aspects/CSharp14/` (one directory per feature; `NullConditionalAssignment_Template.cs` shows a C# 14 construct in a template, `FieldKeyword_Template.cs` shows one in an introduced accessor, `ExtensionMembers_*.cs` show target code); `Tests/Aspects/LanguageVersion/` for LAMA0282; `Standalone/TemplateLanguageVersion14` for LAMA0232 (copy as `TemplateLanguageVersion15`); `Tests/Aspects/DesignTimeInvalidCode/UnknownAccessorInTemplate.cs:5-8` for `@RequiredConstant(ROSLYN_5_10_0_OR_GREATER)`. Note that `@LanguageVersion(15.0)` is enough to skip a test on the 5.0.0 variant: an integral version that Roslyn does not recognise sets `SkipReason` instead of throwing (`TestOptions.cs:681-699`), so `@RequiredConstant` is only needed when the expected output differs. There is no `CSharp14` directory in `Metalama.Framework.Tests.TemplateTests/Tests` (categories at `Tests/`: `Dynamic`, `Syntax`, `UnsupportedSyntax`, ...), so C# 15 template-compiler tests would be the first of their kind there; `Tests/Syntax/` is the natural place.
- Consequence class: build or restore error (`ToDisplayStringSafe` throw in LAMA0051/LAMA0052 paths, `.t.cs` mismatches) if the constants are raised piecemeal; no impact until then.
- Size: M (constants, tests, doctrine text); the product decision is separate.
- Confidence: verified.
- Open questions: the Rider default (above); whether `CSharpParseOptions` on Roslyn 5.0 rejects `(LanguageVersion) 1500` with an error or accepts it silently, which decides how a C# 15 compile-time assembly fails in a Roslyn 5.0 host.

### TP-9. The design-time hashers do not hash the stripped members

- Where: `eng/src/GenerateMetaSyntaxRewriter/Generator.cs:615-712` (`:656-663`, `:684`); `Metalama.Framework/src/Metalama.Framework.DesignTime/Pipeline/Diff/DiffStrategy.cs:73-84`; `Metalama.Framework/src/Metalama.Framework.DesignTime/Pipeline/Diff/BaseCodeHasher.cs:19`.

- Consequence class: silent wrong output at design time (stale compile-time assembly or stale generated partial classes until another edit), before regeneration; no impact after regeneration.
- Proposed change: none beyond TP-1; add the union rename case to `Metalama.Framework.Tests.UnitTests/Utilities/HasherTests.cs` once regeneration has happened.
- Size: S.
- Confidence: verified.
- Open questions: none.

# 06. The `net11.0` user target framework, runtime dependencies, patterns and documentation

Analysis of `/home/user/Metalama` on branch `topic/2027.0/26-09-03-update-eng-7e3j07`, read on 2026-09-03. Nothing was built or run. Roslyn facts come from the scratchpad copies of the `dotnet/roslyn` `main` sources (`scratchpad/roslyn/*`, `scratchpad/api/*`), which are a July 2026 prerelease state.

## Summary

1. No shipped package needs a `net11.0` asset: every product project targets `netstandard2.0`, `net472` and `net10.0` (or `net10.0-windows`), the Core flavour is `net10.0` by design, and the tools roll forward to .NET 11 through `RollForward=Major`. The work is in the build container, the test matrix and a few stale defaults.
2. The build container installs only the .NET 10 SDK 10.0.400 (`eng/src/Program.cs:26`), so no test project can add `net11.0` today; `SupportedPlatform.TestedTargetFrameworks` says so explicitly.
3. `MaximumSdkVersion` is `11.0` while the .NET 11 SDK reports `11.0.100`; the `VersionGreaterThan` comparison in `Metalama.Framework.targets:412` will report `LAMA0601` on every build with the .NET 11 SDK unless the comparison is narrowed to major.minor (plausible, to be verified first).
4. The nested compile-time reference project still restores `net8.0` by default (`CompileTimeAssemblyLocator.cs:43`), and unit and aspect tests observe `Project.TargetFramework == "net8.0"` because `DefaultProjectOptions` still returns it (`DefaultProjectOptions.cs:56`).
5. Runtime dependency pins do not have to move for .NET 11: the `*LatestVersion` values are on the 10.0 line that Roslyn 5.10 requires, the user-surfacing 8.0.x pins are the subject of #1903, and the .NET 11 SDK changes only package pruning and the end-of-life warning for `net8.0`, not the audit data.
6. A C# 15 union declaration is `TypeKind.Struct` in Roslyn, so every pattern treats it as a struct: `[Observable]` rejects it with the existing diagnostic, Multicast matches it as `MulticastTargets.Struct`, Contracts require `U?`, and Caching keys and serializes it as an opaque struct, which is where the only semantic defect lies (type-name-only cache key, and a `default` value after JSON round-trip).
7. Closed classes, labeled `break`/`continue` and `with(...)` elements reach no pattern-specific code path; the Observability syntax walker and the Metrics visitors handle the new nodes through `DefaultVisit`. Extension indexers depend on how the code model exposes them (theme 03), and no Patterns test covers extension members yet.
8. Documentation to update is concentrated in `platform-support.md`, `extensibility.md`, `testing.md`, `compile-time-target-frameworks.md`, `Directory.Packages.props` comments and the two `CLAUDE.md` command examples; `NOTES.md` holds a single breaking-change entry and no convention beyond a heading per change.

### UT-2. `MaximumSdkVersion=11.0` reports LAMA0601 for every .NET 11 SDK

- Where: `Metalama.Framework/src/Metalama.Framework.Package/build/Metalama.Framework.props:33` (`<MaximumSdkVersion>11.0</MaximumSdkVersion>`), `Metalama.Framework.targets:399` (`_MetalamaSdkVersion` is `NETCoreSdkVersion` with the prerelease suffix removed, for example `11.0.100`), `Metalama.Framework.targets:410-413` (`$([MSBuild]::VersionGreaterThan($(_MetalamaSdkVersion), %(_MetalamaPlatformRequirement.MaximumSdkVersion)))`).
- What happens today: with SDK 10.0.400 the comparison `10.0.400 > 11.0` is false and nothing is reported. With SDK 11.0.100 the comparison is `11.0.100 > 11.0`. MSBuild's `VersionGreaterThan` parses through `SimpleVersion`, which treats missing components as zero, so `11.0` is `11.0.0.0` and `11.0.100` is greater. The target framework rule does not have this problem, because `$(TargetFrameworkVersion)` is `v11.0` (`Metalama.Framework.targets:321-322`), which compares equal to `11.0`. The minimum rules are safe for the same reason (`10.0.400 < 10.0` is false).
- Consequence class: diagnostic reported. Every user building with the .NET 11 SDK, which is in the supported set, gets `LAMA0601 'Metalama.Framework' does not support the .NET SDK 11.0.100, which is newer than 11.0`.
- Proposed change: compare the SDK on major.minor only, for example by computing `_MetalamaSdkVersion` as the first two components of `NETCoreSdkVersion`, or document that `MaximumSdkVersion` names the last supported feature band and write `11.0.99999`. Add a scenario `SupportedPlatform.SdkAtMaximum` to `Metalama.Framework/src/tests/Standalone/` with a contributed requirement whose `MaximumSdkVersion` equals the major.minor of the SDK of the build agent and which forbids `LAMA0601`; the existing `Test.LegacySdk` (`SupportedPlatform.ContributedRequirements.csproj:41-43`) uses `1.0` and cannot catch the boundary.
- Size: S.
- Confidence: plausible. The targets were read end to end; the `SimpleVersion` semantics of MSBuild were not executed here and must be checked with one `dotnet build` under an 11.0.100 SDK before anything else in this report.
- Open questions: none beyond the verification.
